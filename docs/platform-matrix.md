**ADR-53 (Streaming token cursor `tokenize`) run once on both platforms**: Windows `bench/results/2026-11-11-windows-tokens/`, Linux `bench/results/2026-11-11-linux-tokens/`. **Measurement methodology changed**: `bench/run.py` and `bench/tokens_timings.py` now split wall-clock time and peak memory into two separate passes. The old implementation performed sampling within the timing loop, and Windows `time.sleep(0.001)` actually sleeps for the full 15.6 ms clock interrupt, causing each figure to be inflated by over ten milliseconds, with "faster operations being inflated more." Therefore, wall-clock figures archived in this round cannot be compared across sessions with earlier Windows archives, as the earlier Windows figures are skewed high; Linux sampling uses `/proc`, with impact ≤1 ms.

`tokenize` is **not a general-purpose iterator**: it has only one form, "string + delimiter", lacks `len` (counting requires consuming the entire stream), its cursor cannot be `print`ed / put into containers / returned, and the delimiter has a 16-byte limit. `split` remained completely unchanged—what got faster was simply the same program written using a different idiom.

**ADR-54 (`args()` converted to UTF-8 on Windows) run on both platforms**: Windows `bench/results/2026-11-11-windows-argv-utf8/`, Linux `bench/results/2026-11-11-linux-argv-utf8/`. Defect pattern: the Windows CRT passes command lines to `main` according to the ANSI code page, causing paths containing Chinese characters to enter the program as GBK bytes (`len(args()[1])` = 8), whereas the runtime decodes paths as UTF-8, leading `_wfopen` to open a non-existent name—yet Chinese string literals in the source code always worked properly. Fix: `args()` converts each argument from CP_ACP → UTF-16 → UTF-8, falling back to raw bytes upon failure. Both platforms passed 35 unit + 161 integration tests (a new test case uses a Chinese absolute path as an argument, successfully runs `write_file` + `read_file`, and asserts a length of 12 instead of 8; **reverting the fix causes this test case to fail**), 30 `--leak` test cases PASSED, and 37 examples passed `check`.

Cost: Programs calling `args()` on Windows retain `<windows.h>` (Win32 is used for conversion), generating 16,317 bytes of C for a read-only argument probe; programs not using `args()` are unaffected—`print(1)` remains at 11,299 bytes and still carries `/* windows.h omitted */`, while `float_math.ae` similarly strips the header (after ADR-55, `print(1)` becomes 15,243 bytes). Edge case: When the command line enters `main`, it is already ANSI bytes; characters that cannot be represented by the code page (such as some emojis) are lost at the CRT step and cannot be recovered by this fix; `__wgetmainargs` for retrieving the raw UTF-16 command line caused a segmentation fault on this UCRT toolchain and has been documented and abandoned.

**ADR-55 (`print` written as UTF-16 on Windows consoles)**: Windows `bench/results/2026-11-11-windows-console-utf8/`, Linux `bench/results/2026-11-11-linux-console-utf8/`. Defect pattern: The runtime always wrote correct UTF-8 bytes, but the console decoded the received bytes according to **its own output code page** (936 for Chinese Windows), causing `print("中文测试")` to appear on screen as `涓枃娴嬭瘯`. The forensics method involved building a custom CP-936 console, handing the `CONOUT$` handle to the program under test, and reading back the screen buffer using `ReadConsoleOutputCharacterW` (which stores the exact characters seen by the user): narrow-writing the exact same bytes yielded `U+6D93 U+E15F U+6783 U+5A34 U+5B2D U+762F`, while `WriteConsoleW` yielded `U+4E2D U+6587 U+6D4B U+8BD5`. Fix: The four forms of `print` now converge at a single join point, checking at runtime whether stdout is a console—if so, it converts to UTF-16 in chunks (1 KiB blocks, 2 KiB on the stack, block boundaries avoid splitting characters) and **combines the newline into the same write operation**, otherwise writing raw bytes as-is; the four Win32 entry points are declared inline within the body of the functions that use them, avoiding the inclusion of `<windows.h>` (top-level text is always preserved, and inner-function declarations are stripped alongside their functions).

Both platforms passed 35 unit + 162 integration tests (new test cases cover byte-by-byte output for all four forms plus Chinese string literals), 30 `--leak` test cases PASSED (Windows 2 blocks / Linux 0 blocks), Linux `--sanitize` 30 test cases yielded 0 reports, and 37 examples passed `check`; generated C for both `print(1)` and `args`+`print` programs passed strict C11 syntax checks (the latter simultaneously retains `windows.h` and self-declared entry points, coexisting without conflict). Console edge cases and chunking: 1022 ASCII characters + one 3-byte character precisely spanning the 1023-byte boundary were byte-for-byte recovered, 3,000 Han characters (multiple chunks) were byte-for-byte recovered, and invalid UTF-8 bytes are displayed as U+FFFD on the console while passing through raw in pipes.

Cost: Generated C for `print(1)` grew from 11,341 to 15,243 bytes (+34%), non-printing programs from 11,286 to 11,811 (+525), and `args`+`print` from 15,178 to 20,742; build time went from 74.6 to 75.7 ms (9 alternating runs, within noise); console throughput for 20,000 lines went from 860.3 to 832.0 ms (one `WriteConsoleW` per line, no regression), and redirection to a file went from 17.6 to 18.2 ms (the pipe path incurs only one extra call and one check); conversion introduces no new allocations. Edge cases: Characters unrepresentable by the console (such as emojis) display as U+FFFD, which is standard console behavior (probes directly calling `WriteConsoleW` exhibit identical behavior under both the 936 and 65001 code pages), and we do not claim that "emojis can also be displayed"; only stdout is handled, and runtime error messages remain ASCII `fprintf`; the console code page is not modified, leaving the parent shell environment unchanged upon exit.

**ADR-56 (map load factor 0.75 → 0.5)**: Windows `bench/results/2026-11-11-windows-map-loadfactor/`, Linux `bench/results/2026-11-11-linux-map-loadfactor/`. Attribution before modification: Four probes decomposed map load into `arith` (3.76 / 3.57 ms), `key` (32.55 / 30.82), `hit` (60.71 / 55.67), and `put` (58.27 / 53.76, all ae / Rust respectively), concluding that "arithmetic is on par, key construction accounts for half, and the performance gap lies in probe counts." Two changes were made: growth threshold changed from 3/4 to 1/2 (effective load factor 0.61 → 0.31, average probes ~1.3) and `ae_str_eq` takes a byte loop for strings ≤8 bytes (eliminating the `memcmp` call).

Both platforms passed 35 unit + 163 integration tests (added `map_grows_reuses_removed_slots_and_keeps_every_survivor`), 30 `--leak` test cases PASSED (Windows 2 blocks / Linux 0 blocks, covering the slot table expansion and old table deallocation path), Linux `--sanitize` 30 test cases yielded 0 reports, and 37 examples passed `check`.

Linux 11 alternating pairings: map load dropped from 67.92 to 58.08 ms (**1.172×**, all ratios ≥1.12), `hit` improved by 1.159×, and `put` by 1.178×; four-load suite (5 interleaved runs) for map was **57.72 ms / 3.14 MB**, Go 58.29 / 7.48, Rust 55.37 / 2.98, Python 236.88 / 9.36—shifting from "trailing Rust by 27%, tying with Go" to "faster than Go, trailing Rust by 4%." The cost is peak memory increasing from 2.44 to 3.43 MB (+41%, roughly 64 bytes of slot overhead per element); a 5/8 load factor yielded only a 1.03× speedup while incurring the same memory overhead, so it was not adopted.

Boundary: The gains are workload-dependent (significant for probe-intensive tables, negligible for small tables), while the memory cost applies to all tables; `keys` are sorted by byte order, and iteration order remains consistent with observable behavior. The hash function remains unchanged, and we do not claim that "our map is faster than Rust's." A side note on a measured but unfixed issue: `map_get` allocates a reason string on misses, taking ~6.9 ms for 1M misses (compared to 0.5 ms for Rust's `Option<i64>`); this is noted as a candidate for the next cycle.

**ADR-57 (Moving map state bits out of slots, 32 → 24 bytes)**: Windows `bench/results/2026-11-11-windows-map-states/`, Linux `bench/results/2026-11-11-linux-map-states/`. The cost of ADR-56 was documented: ~64 bytes of slot overhead per element, with a peak of 3.43 MB. This step moves the `unsigned char state` from the slot into a parallel `unsigned char *states` array (1 byte per slot), leaving the slot with only `{ key, value }` totaling 24 bytes. The probe chain now reads the 32 KB state array (resident in L1/L2) before accessing the slot.

Both platforms passed 35 unit tests + 164 integration tests (new test: `keys_after_removal_skips_tombstones_and_sees_reused_slots`), 30 `--leak` cases passed, 30 Linux `--sanitize` cases reported 0 issues, and 37 examples passed `check`.

Linux 11-run alternating pairing: map load 1.012×, `hit` 1.007×, `put` 1.027× (on par); peak memory **3.43 → 2.90 MB (−15%)**, table body 1,048,576 → 819,200 bytes (−22%). Four-load suite: map 59.88 ms / 2.86 MB, Rust 56.99 / 2.91, Go 69.71 / 7.49—**memory is now lower than Rust's, while time remains ~5% slower**. Generated C `print(1)` 15,243 → 15,302 (+59). Boundary: This is an internal layout change; `keys()` order and hashing remain unchanged; time is "on par," not "faster."

Design highlights: The base of `slice_view` can now be a "variable.string_field," but the borrowed object is the **entire variable**—moving the variable, assigning to it as a whole, or writing to any of its fields is rejected for the duration of the view's lifetime (field write paths previously **did not check** `borrows`; this has been tightened). Nested fields, `v[0].name`, and non-string fields still trigger errors as before. **This is not field-level borrowing, nor is it a general-purpose borrow checker**; views remain read-only and cannot be used as return values or fields. Zero added overhead for generated C or runtime.

## Known Platform Differences (Transparently Disclosed)

- Executable naming: Windows `.exe`; Linux has no suffix and requires the executable bit (`build` automatically sets 0755).
- Artifact size: Same program is ~61–64 KB on Windows, ~16.8 KB on Linux (linker and CRT differences).
- Address/Undefined Behavior Sanitizers: MinGW lacks an ASan runtime; verified only on Linux; Windows relies on the test matrix and generated C review.
- Allocation count baseline: Windows 2 blocks, Linux 0 blocks; subtract respective baselines when comparing.
- Path encoding: Windows internal use of UTF-8 source and non-ASCII paths verified (e.g., `程序.ae`); Linux is natively UTF-8.
- Strict ISO C: Generated files use only C11 standard interfaces and do not inject feature macros like `_POSIX_C_SOURCE`. Thus, the same C code compiles under glibc, musl, and `-std=c11 -pedantic-errors`. The trade-off is the inability to use POSIX-specific interfaces (time must use `timespec_get`, so monotonic clocks are unavailable).
- Stdin line endings: Both platforms read as binary; `\r\n` is not translated; differences exist only in text provided by the user.
- Stdout line endings: Generated C uses `fputs`/`printf`/`fputc('\n')` to write to stdout. Windows text mode translates every `\n` to `\r\n`, while Linux keeps `\n`. Cross-platform comparisons must normalize line endings first; Rust integration tests and example comparisons do this. This is a CRT difference, not a branch in the generated code.
- C compilation time: The Windows branch must parse `<windows.h>` **when Win32 capabilities are used** (approx. 690 ms for `-fsyntax-only` alone, approx. 520 ms with `WIN32_LEAN_AND_MEAN`). After ADR-39, programs not touching this layer no longer include this header (same-run comparison: with header 945.6–1,296.4 ms, without header 252.6–319.6 ms). Linux never preprocesses this branch; the difference between 32.0 ms with header and 31.4 ms without is within measurement noise. Compilation times still differ by an order of magnitude between platforms, and the Windows side varies depending on whether the program uses file/directory/clock/environment/subprocess capabilities; results from `bench/build_timings.py` must be viewed separately and cannot be merged into a single "compilation speed" number, nor can Linux numbers represent the Windows experience, nor can absolute cross-session values be treated as precise speedup ratios.
- Subprocesses: `run_command` does **not** go through a shell on either platform (Windows uses `CreateProcessW` directly, POSIX uses `execvp` directly), so built-in commands like `echo` or `dir` must be explicitly written as `cmd` with `/c`. When killed by a signal, POSIX reports `128 + signal_number`, while Windows provides the exit code directly—this is the only intentionally preserved semantic difference.
