# ae Current Prototype Semantics (Unstable)

This document describes only the subset already implemented and does not represent the final design of the language.

## Lexical Structure

Source files are encoded in UTF-8. Identifiers start with an ASCII letter or underscore, followed by letters, underscores, or digits; keywords are reserved (`fn`, `let`, `var`, `print`, `if`, `else`, `while`, `for`, `in`, `return`, `break`, `continue`, `assert`, `true`, `false`, `use`, `struct`, `enum`, `match`). Files can import others at the top using `use "relative/path.ae";`: paths are resolved relative to the importing file's directory, loaded depth-first, and circular imports trigger an error. Function names must be unique across files, and `main` must be unique across the entire program (library files do not require `main`). Top-level items visible across files must be marked `pub` (`pub fn`, `pub struct`, `pub enum`); unmarked items are visible only within the current file (see "Modules and Visibility" below). Tokens are separated by whitespace; `//` comments extend to the end of the line. String literals use double quotes and support `\n`, `\t`, `\r`, `\\`, and `\"` escapes; raw newlines or NUL bytes are not permitted. The program must contain exactly one `fn main() { ... }`, and other functions may be defined. Statements are terminated by semicolons.

## Values and Computation

Scalar types include the signed 64-bit integer `i64`, the boolean `bool`, and the IEEE 754 binary64 floating-point `f64`; there are also owned `string` types and fixed-length `i64` arrays. Integer literals currently only support values from 0 to 9223372036854775807; unary negation and subtraction can produce negative numbers. Operators `+`, `-`, `*`, `/`, `%` are supported; multiplication, division, and modulo have higher precedence than addition and subtraction. All are left-associative, and unary `-` and `!` bind tighter than all binary operations. Operands are evaluated from left to right. Division and modulo truncate toward zero, and the remainder carries the sign of the dividend. Overflow and division by zero cause the program to exit with a non-zero status, reporting the row and column of the operator to standard error; these checks are not disabled in either development or optimized builds.

Comparisons `==`, `!=`, `<`, `<=`, `>`, `>=` operate on two `i64` values; `==` and `!=` can also compare two `bool` values or two `string` values (by content), producing a `bool`. `&&` and `||` use short-circuit evaluation (the right operand is evaluated only if the left operand does not determine the result), and `!` performs boolean negation. Comparisons cannot be chained (e.g., `a < b < c` is rejected due to a type error).

`let x = expression;` declares an immutable variable; `var x = expression;` declares a mutable variable. A binding may carry a type annotation — `let v: vec[f64] = vec[];`, `var n: i64 = 0;`, `let p: Point = Point { .. };` — and the initializer must agree with it (`the annotation says i64, but the initializer is f64`); an empty `vec[]` takes its element type from the annotation, which is how an empty vector of a non-i64 element starts. A borrow annotation (`let r: &P = …`) is rejected: borrows exist as parameters and match bindings only. Variables cannot be used before declaration, and redeclaration is forbidden; assignment requires type consistency. Curly braces introduce lexical scopes; inner scopes can read outer variables subject to mutability rules. Inner variables are invisible after leaving the block and cannot shadow currently visible names. `print(x);` writes to standard output in decimal (for integers), `true`/`false` (for booleans), or the string content, followed by a newline; `print("text");` outputs the literal directly. Output errors cause the program to exit with a non-zero status. **Output Encoding**: Text produced by the program is UTF-8. When written to pipes or files, these bytes are written as-is without conversion. When written to a Windows console, the runtime converts it to UTF-16 for the wide-character interface (ADR-55), because the console decodes narrow bytes using its **own code page** (e.g., 936 for Chinese Windows), and passing raw UTF-8 bytes would result in mojibake. Whether the console can display a specific character is determined by the console itself: characters it cannot represent (such as emojis on `conhost`, regardless of the code page) are displayed as `U+FFFD`, while the same text written to a file remains valid, complete UTF-8. `assert(condition);` reports the row and column of the assertion and exits with a non-zero status if the condition is false.

## Floating-Point `f64`

`f64` is IEEE 754 binary64; the C backend uses `double`. `f32` and decimal floating-point types do not yet exist. Literals must contain a decimal point or an exponent: `1.5`, `0.25`, `1e3`, `2.5e-3`; `1..2` remains a half-open range, and `1.field` remains a field access. Non-finite literals (e.g., `1e400`) and literals that underflow to zero (e.g., `1e-400`) trigger a lexical analysis error; the compiler will not silently replace user-provided values with `inf` or `0`.

**No Implicit Conversion**: `1 + 2.0` is a type error; one must write `to_f64(1) + 2.0` or `1 + to_i64(2.0)`. `to_f64(n)` succeeds only if `|n| ≤ 2^53`; values exceeding this lose precision and cause a runtime failure. `to_i64(x) -> IntResult` accepts only finite integers within the `i64` range; `2.5`, `1e308 * 10.0`, and `1e30` return "not an exact integer," "not a finite value," and "out of i64 range," respectively.

`+`, `-`, `*`, `/` operate on two `f64` values; `%` is defined only for `i64` and is rejected for floating-point. `/` follows the same rules as integer division: division by `0.0` reports a failure and exits rather than returning `inf`. Overflow results in `inf`, and underflow results in subnormal numbers or `0`, following IEEE standards, with consistent results between `-O0` and `-O2` (fast-math is not used). All six comparison operators are available with IEEE semantics: any comparison with NaN is false, except `!=`, which is true. `Eq`/`Ord` constraints therefore allow `f64`, but this does not imply it is a total order.

**Text representation is canonical** (shared by `print` and `to_string`): `nan`, `inf`, and `-inf` have fixed spellings. Finite values use the "shortest valid representation for round-tripping," choosing the shorter of fixed-point or scientific notation (preferring fixed-point if lengths are equal). The exponent is written as `e` followed by a sign and the minimum number of digits. If the result has neither a decimal point nor an exponent, `.0` is appended; thus, `print(1.0)` outputs `1.0`, `print(-0.0)` outputs `-0.0`, `print(0.1)` outputs `0.1`, `print(1.0 / 3.0)` outputs `0.3333333333333333`, and `print(1e16)` outputs `1e+16`. This rule is implemented by the runtime and does not depend on C library `printf` variations (UCRT and glibc spell NaN differently).

### Mathematical Built-ins (ADR-60)

There are 13 built-ins, all of which take `f64` arguments and return `f64`. 11 map 1:1 to the C library: unary `sqrt`, `abs` (C's `fabs`), `floor`, `ceil`, `round`, `exp`, `log` (natural logarithm), `sin`, `cos`, and binary `pow(base, exponent)`, `atan2(y, x)` (same argument order as C). Two are **runtime-implemented**: `min(a, b)` and `max(a, b)` (ADR-64). These are reserved names and cannot be used as functions, variables, parameters, or pattern bindings. **No implicit conversion**: `sqrt(4)` (an `i64` argument) is a compilation error; one must write `sqrt(to_f64(4))` or `sqrt(4.0)`. Arity is fixed; providing too many or too few arguments triggers an error.

**Semantics are IEEE/C library semantics, not language-level checks**: Domain errors return IEEE values—`sqrt(-1.0)` is `nan`, `log(0.0)` is `-inf`, and `pow(0.0, negative)` follows IEEE—and the program continues execution. This differs from the `/` operator, which reports a failure on division by zero; the check contract for `/` belongs to the language itself (consistent with integer division), whereas mathematical functions expose the established representation of IEEE doubles to numerical code, as terminating on NaN would make standard numerical patterns like "check domain before calculating" impossible. `round` is the C `round` function: **0.5 rounds away from zero** (`round(2.5)` is `3.0`, `round(-2.5)` is `-3.0`), not banker's rounding. `min`/`max` are runtime functions rather than `libm`: **NaNs are ignored** (if one side is NaN, the other is returned; if both are NaN, NaN is returned), and **±0.0 ties follow a total order** (`min(-0.0, 0.0)` is always `-0.0`, `max` is always `0.0`, regardless of argument order)—`fmin` in `libm` does not specify behavior for this tie, and calling it directly would make printed text platform-dependent. The generated C code calls `libm` symbols directly (`<math.h>` is included in every program, as the float formatter requires it); Linux link lines include `-lm` (a merged shell since glibc 2.35, but required for older versions), and Windows provides these symbols via the C runtime.

**Cross-platform text**: Exact values (`sqrt(4.0)` → `2.0`, integer values of `floor`/`ceil`/`round`, `exp(0.0)`, `log(1.0)`, `sin(0.0)`, `cos(0.0)`, `pow(2.0,10.0)`, and all outputs of `min`/`max` including `min(-0.0, 0.0)`) and `nan` spelling are consistent across both platforms (text is self-generated by the runtime, see above); transcendental functions (like `sin(1.0)`) may differ by up to 1 ulp across different libms, so **use tolerances for cross-platform comparisons** (`abs(value - expected) < 1e-15`) rather than byte-by-byte comparison of printed text. See `examples/math_basics.ae` for examples.

`f64` can be used as parameters, return values, struct fields, enum payloads, and generic arguments (`Option[f64]`), and is also the element type of `vec[f64]` (ADR-61, see the vectors section below); `map[string, f64]` is available (ADR-65, see the map section below); `&f64` cannot be borrowed (read-only borrows are restricted to `string`, `vec`, `vec[string]`, `vec[f64]`, fixed arrays, and user structs since ADR-0184; maps cannot be borrowed). Aside from mathematical built-ins, `f32` and decimal numbers are not yet supported.

## Owned Strings and Move Semantics

`string` values own a byte buffer on the heap. Initialization, pass-by-value, assignment, and `return` **move** ownership; after a move, the original variable can no longer be used at compile time (if moved inside a branch, the branch merge point conservatively treats it as moved). Re-assigning to a moved variable is a valid re-initialization; on the right-hand side of the same statement, the move destination cannot be moved from itself. `+` concatenates two strings and consumes both operands; `print` and `len` borrow without consuming. `len(s)` returns the number of UTF-8 bytes in the string.

Deallocations are inserted at compile time: block exits, early returns, `break`/`continue` (only for strings declared inside the loop body), and function return paths are all covered; deallocation operations are idempotent (the pointer is zeroed out after deallocation), preventing double-free or use-after-free even if a divergence occurs between the analyzer and the generated code—a runtime null check serves as a final line of defense before each read of a string variable. Memory allocation failures cause the program to report its position and exit with a non-zero status. Inside a loop body, **owned values from outside the loop cannot be moved out** (`let t = s;`, `f(s)`, `return s`): since loop bodies execute repeatedly, the next iteration would read a moved value, so the compiler rejects this directly unless the variable is reassigned before the end of the loop body (see "Control Flow").

## Control Flow

`if condition { ... } else { ... }`: The condition must be a `bool` expression; `else if` chains are supported, and the trailing `else` can be omitted. `while condition { ... }` re-evaluates the condition on every iteration. `for i in start..end { ... }` iterates over a half-open range: bounds are evaluated exactly once from left to right, `i` is an immutable `i64` within the loop scope, and the hidden increment is checked arithmetic (safely failing if the maximum value of `i64` is reached). `for x in vector_variable { ... }` iterates over elements by value: for an `i64` vector, `x` is an immutable copy; for a `vec[string]`, `x` is an element view; for a `vec[f64]`, `x` is an immutable `f64` copy. The length is captured once at the start of the loop. The iterated vector is borrowed for the entire duration of the loop body; consequently, **moving or mutating it in-place** (`push`/`pop`/index assignment) inside the loop body is rejected at compile time—although the length snapshot makes `push` semantically feasible, the current implementation chooses a conservative approach. `break` immediately exits the innermost loop; `continue` skips the remaining body—still performing the increment in a `for` loop. `break`/`continue` are only permitted inside loops. The same move rule applies to all three loops: **loop bodies must not move out owned values declared outside the loop** (`let t = s;`, `f(s)`, `return s`) unless they are reassigned before the end of the current loop body—otherwise, the next iteration would read a moved value; diagnostics point to the loop keyword. Owned values declared inside the body of a `while` or either type of `for` loop are deallocated at the end of each iteration.

`exit(status_code);` immediately terminates the process; the status code must be an `i64` (the process exit code is truncated as an `int`, and on POSIX systems the shell inspects only the low 8 bits). Before termination, standard output is flushed, and all live owned values are deallocated—meaning "print then exit" will not lose the last line, and allocation accounting remains balanced. Statements in the same block following an `exit` are unreachable but must still pass parsing. Functions that terminate exclusively via `exit` and never return values can be declared with any return type without requiring a `return`.

## Dynamic Vectors

`var v = vec[1, 2];` creates an owned, growable vector (`vec[]` denotes an empty vector). `push(v, x);` and `pop(v);` are statements: they require a mutable local variable, perform in-place mutation, and do not transfer ownership; calling `pop` on an empty vector causes an error. `v[i]` for reading and `v[i] = x;` for writing both perform bounds checking against the current length (writes check the index before evaluating the right-hand side). `len(v)` yields the runtime length. Like strings, vectors own heap resources: assignment, pass-by-value, and `return` move ownership; post-move usage is caught at compile time with runtime null checks as a fallback; scope exits and jump paths trigger idempotent deallocations. `&vec` parameters are read-only borrows: they support `len`, indexing, and re-borrowing, but do not allow writing, push/pop, moving out, or outliving the borrowed value; they are passed at call sites using `f(&v)`. Vector elements are `i64` by default; `vec[T]` names another element type (see the `vec[f64]`, `vec[string]` and generic-element sections below); the built-in names `vec`, `push`, `pop`, `len`, `read_file`, `write_file`, and `bytes` are reserved.

## File and String Utilities

`read_file(path) -> string` reads an entire file into an owned string; `write_file(path, content) -> i64` writes content and returns the number of bytes written. Both borrow their parameters, and paths are interpreted as UTF-8 (on Windows via UTF-16 wide-character APIs, allowing non-ASCII paths); failures report runtime errors with line and column positions. `bytes(s) -> vec` converts a string into a vector of bytes for byte-level processing. `contains(s, sub) -> bool` performs substring searching (platform-optimized implementation, borrows both parameters, empty substrings yield true); `starts_with(s, prefix) -> bool` and `ends_with(s, suffix) -> bool` perform byte-level prefix and suffix comparisons (empty strings yield true)—therefore, checking file extensions requires `ends_with(name, ".txt")`, as `contains` would also match `a.txt.bak`; `trim(s) -> string` returns an owned copy with leading and trailing ASCII whitespace (spaces, `\t`, `\n`, `\r`, `\v`, `\f`) removed, trimming only at character boundaries to avoid corrupting multi-byte characters; `slice(s, start, end) -> string` returns an owned slice copy, with out-of-bounds accesses reporting positions. Strings now carry a length (`len`/`slice` operations are O(1)), while their buffers remain NUL-terminated for C interoperability; `len`/`bytes` count precisely by length (including embedded NULs). `read_file`, `write_file`, `bytes`, `contains`, `starts_with`, `ends_with`, `trim`, and `slice` are reserved names.

**Directories and Paths**: `try_list_dir(path) -> DirResult` returns entry names within a directory (excluding `.` and `..`, sorted in byte-lexicographical order), returning `Err(description)` on failure; `path_exists(path) -> bool` and `path_is_dir(path) -> bool` perform queries only. All three accept either owned strings or views.

## String Searching `find`

`find(text, needle) -> IntResult` returns the **byte index of the first match**: a hit evaluates to `Ok(index)`, a miss to `Err("substring not found")`, and an empty `needle` returns `Ok(0)`. Both parameters accept owned strings or views and are borrowed rather than moved; the result must be `let`-bound before a `match` and cannot be written as a bare expression statement. `find` is a reserved name and cannot be redefined.

```ae
fn main() {
    let at = find("name=ae", "=");
    match at {
        IntResult::Ok(n) => { print(n); }          // 4
        IntResult::Err(reason) => { print(reason); }
    }
}
```

Indices are calculated by **byte**, consistent with `len`/`slice`: `find("中文 abc", "abc")` returns 7, not 3. The implementation uses `memchr` to locate the first byte followed by `memcmp` for comparison; the success path performs no memory allocation, while the failure path only allocates the `Err` error text (which is freed by the result enum). The worst-case complexity is O(n·m) with no preprocessing table; it is not an optimal implementation for long patterns or text with many repeating leading bytes.

A known discrepancy with `contains`: `contains` uses `strstr`, which stops when encountering a NUL byte in the middle of a string; `find` searches by explicit length, so embedded NULs are treated as ordinary bytes. Consequently, for inputs containing embedded NULs, the two may yield different conclusions—this is the actual behavior of the existing implementation; the documentation does not obscure this, nor will `contains` be silently modified in this cycle.

## Unicode and Character Boundaries

`len` and `slice` operate by **byte** (strings are UTF-8 byte sequences, and both are O(1)). To avoid slicing into invalid UTF-8, `slice`/`slice_view` terminates and reports `string index splits a UTF-8 character` if the index falls in the middle of a character—the check only examines a single byte and remains O(1); `start`/`end` equal to `len` are considered valid boundaries.

Processing by character is handled by two functions: `utf8_len(s) -> i64` returns the number of characters (code points, i.e., the number of bytes that are not "continuation bytes"), and `utf8_prefix(s, n) -> string` returns an owned copy of the first `n` characters (if `n` exceeds the character count, the entire string is copied; negative values result in an error). `utf8_len("中文 😀 abc")` is 8, while `len` is 15; `utf8_prefix(..., 2)` yields `中文`.

The rules only guarantee that **no new** broken sequences are introduced: invalid bytes originating from files or argv are permitted and processed as-is (`bytes`/`slice` both support this). Characters are counted by code point; combining characters and grapheme clusters are not handled. `split`/`contains`/`lines`/`path_*` still match delimiters by byte (ASCII delimiters are unaffected). `utf8_len`/`utf8_prefix` are reserved names.

## Fixed-Length Arrays

`let a = [1, 2];` declares an immutable array, and `var a = [1, 2];` declares a mutable array. Array elements are integer expressions evaluated from left to right; array length is between 1 and 4096. Only array literals are allowed during declaration; whole-array assignment, pass-by-value, returning arrays, or nested arrays are not supported. `a[i]` performs a read, and `a[i] = value;` requires a mutable array. Indices must be integers; if negative or greater than or equal to the length, the program reports the index location and exits with a non-zero status. Writes calculate and check the index before calculating the right-hand side. `len(a)` is a compile-time constant (requires a bare array variable). Optimized builds maintain the same checks.

## Functions

`fn add(a: i64, b: i64) -> i64 { return a + b; }` defines a function; return types can be `i64`, `bool`, `string`, or `vec`. Parameter types can be `i64`, `bool`, `f64`, `string` (by value, move), `vec` (by value, move), `vec[f64]` (by value, move, ADR-61), `&vec` (read-only borrow), `&vec[string]` (read-only borrow of a string vector), `&vec[f64]` (read-only borrow, ADR-61), `&Struct` (read-only borrow of a user struct, ADR-0184), `&mut Struct` (exclusive mutable borrow, field writes through the pointer, ADR-0185), `&string` (read-only borrow of a string, bound as a view), enums or structs (by value, move), or `&[i64; N]` (read-only borrow of an array), up to 64 parameters. For `&string`, arguments are written directly at the call site (`f(name)`, `f("literal")`, `f(view)`), involving no moves or copies; within the function body, they are used according to view rules (including `+` concatenation, which performs a copy). Borrowed values have no independent storage: `let q = borrowed_param;` is rejected; borrows can only exist as parameters or `match` bindings. Arguments are evaluated from left to right; string arguments move ownership. Functions can be defined before or after the call site; self-recursion and mutual recursion are supported. All paths must explicitly return a value; the compiler currently conservatively recognizes only direct `return` or both branches of an `if`/`else` returning. `main` does not accept arguments or return values. `len` is a built-in function and cannot be redefined. Recursion depth is limited by the system stack.

## Read-Only Array Parameters

Function parameters can be written as `a: &[i64; 3]`. When calling, pass a local array or a read-only array parameter of matching length explicitly using `f(&values)`. The borrow exists only for the duration of the call and can be re-borrowed by other functions; the called function cannot write to, store, or return the borrow. This is a restricted read-only parameter, not a full borrow-checking or ownership system. Indices still perform boundary checks.

## Toolchain

`ae check|emit-c|fmt|test|run|build|cache|deps|version`. `check` performs only lexical, syntactic, and semantic analysis (pure frontend, no C compiler required); `check --json <file>` (or `<file> --json`) emits one JSON array: `[]` on success, or one or more diagnostic objects on failure. Objects contain `file`, `line`, `column`, `message`, `byte_start`, `byte_end`, `code`, `suggestions`, and `secondary`; byte offsets are zero-based, half-open UTF-8 ranges or both `null` when unavailable. Lines and columns are one-based and columns count Unicode scalar values. The error code is a stable string where assigned, otherwise `null`. Suggestions are optional human-readable guidance and must not be applied automatically. Secondary labels identify related source ranges when known. Consumers should accept additional fields. Text-mode `check` retains its first-error behavior. `build` and `run` artifacts are based on content-addressed caching: keys cover generated C, optimization modes, C compiler flags and their paths, ae version, and target platform; entries include a manifest with `byte_count + SHA-256`, verified before hits, and corrupted entries are deleted and rebuilt; if the compiler identity cannot be queried, caching is disabled for that session (`AE_TIMINGS=1` will explain why). Cache hits are semantically identical to full builds. After changing factors outside the key, such as libc/SDK, run `ae cache clear`. `AE_CACHE` overrides the cache location, `AE_CACHE_LIMIT` limits the total cache size in bytes (unset or `0` means no limit; when exceeded, entire entries are deleted based on LRU), and `cache dir|clear|stats` are used to view and clean ( `stats` displays the current limit). `AE_CC` specifies the C compiler. Optimization modes default based on the command role (ADR-59): `build` delivers artifacts, defaulting to `-O2`, with `--debug` at the end reverting to `-O0`; `run` is for the development loop, defaulting to `-O0`, with `--release` at the end using `-O2`. Both flags are accepted for both commands and must be written at the end (before the `--` forwarding separator); unknown flags result in an error. Both modes maintain identical language semantics and checks, and the same generated C; they differ only in the C compilation `-O` level, with cache keys including the optimization mode and both versions coexisting. `run` forwards arguments after `--` to the executed program (`args()` is visible, including argv[0]); other subcommands do not accept program arguments and will error if provided. `AE_TIMINGS=1` outputs stage duration and cache hit status; `AE_ALLOC_LIMIT=N` limits the cumulative runtime allocated bytes to N, used to deterministically verify allocation failure diagnostics (terminates with "out of memory" and location when exceeded; this is not a memory quota, and non-numeric values are ignored).

## Formatting

`ae fmt file.ae` normalizes whitespace in-place: indentation follows the brace depth (4 spaces per level), spacing between adjacent tokens is determined by a deterministic rule table, line-break structures and the number of blank lines are preserved line by line (no line splitting, side-by-side arrangement, or folding), comments, strings (including escapes), and literal spellings are preserved verbatim as source bytes, alignment gaps before trailing comments are preserved (a single space is added to tight `;//` lines), and the end of the file is terminated by exactly one newline. The line ending style follows the input file (CRLF outputs CRLF, otherwise LF).

The validity threshold is "lexically tokenizable by the compiler", **not a full check**: module files lack their own `main` and cannot undergo independent whole-program checks; files with semantic errors (as long as tokens are lexically valid) will still be formatted—`fmt` only touches whitespace and does not evaluate semantics, and `check` remains the sole semantic threshold. Lexing failures (unclosed strings, illegal characters) result in a fatal error on exit, leaving the file untouched.

Idempotency is structurally guaranteed: spacing depends only on the categories of adjacent tokens, indentation depends only on depth, and a second run produces zero byte-level changes. Precise definition of semantic invariance: the token sequence, line numbers, comments, and string bytes all remain unchanged; the generated C code will differ numerically due to embedded source column numbers (since spaces shift columns), while everything else matches line by line. Write safety: all processing is performed in-memory, no writes occur if the content is unchanged, and writes are performed via a temporary file in the same directory followed by a rename. Formatting 35 examples takes a total of ~300 ms (Windows, including process startup; Linux takes 23 ms; absolute values are not comparable across platforms); the compiler's primary pipeline remains unmodified.

## Testing

`ae test file.ae [filter]` runs the test functions within the specified file; the filter is a substring of the test name (`ae test file.ae trim` only runs tests containing `trim` in their names, and `ok: N passed` counts the filtered amount), an empty match results in an error rather than silently passing, and test signature validation occurs prior to filtering (ADR-62). The test convention is `fn test_<name>() -> i64`: returning 0 indicates success; returning any non-zero value indicates failure, which becomes the exit code of the entire command; failures from `assert` or checked arithmetic follow the existing panic path (stderr outputs the line/column numbers, exit code 1). Each test prints `RUN <name>` prior to execution, `PASS <name>` upon success, and `ok: N passed` upon completion; failure stops execution immediately (subsequent tests are not run), which is the v1 behavior.

The implementation involves zero front-end semantic changes: a token-level scanner identifies test functions, appends a synthesized `main` to a copy of the source file in the same directory, and then proceeds through the regular check, C generation, caching, and execution pipeline; the file copy is automatically deleted across all paths. Functions starting with `test_` that violate the convention (having parameters, a non-`i64` return type, or being generic) are treated as explicit errors rather than being silently skipped; files that define a `main` function or contain no test functions are also rejected. v1 only collects tests from the entry-point file (`test_*` functions in `use` module files are not collected) and does not support filtering or parallelism.

## On-Demand Runtime for C Generation

`emit-c` outputs a self-contained C11 translation unit, but its runtime **only includes functions reachable by the program**. The compiler first splits the "runtime prefix that is byte-for-byte identical for every program" (`runtime.c` + preset enum layouts + `runtime_ex.c`) into top-level units: function definitions, along with includes, macros, type definitions, static data, and comments that must be preserved verbatim. The root set originates from `ae_*` symbols referenced in program suffixes, symbols appearing in non-function text (macro bodies and static initializers can indirectly invoke functions), and the documented embedding entry point `ae_set_allocator`; it then computes a transitive closure along references within the bodies of the retained functions. Under conditional compilation, multiple definitions with the same name (e.g., separate `ae_fopen` implementations for Windows and POSIX) are all retained and participate in the closure scan. Unretained functions have no callers within the compilation unit, and removing them does not alter program semantics, nor does it disable any checked arithmetic, bounds-checking, or deallocation paths.

Consequently, the size of `emit-c` varies with the built-ins used: `fn main() { print(1); }` is approximately 20 KB, while programs utilizing built-ins such as files, JSON, and floating-point numbers are around 25–35 KB; prior to this change, it was fixed at approximately 110 KB. `WIN32_LEAN_AND_MEAN` further eliminates unused Win32 declarations. **Do not use the byte size of the generated C code as a version identifier**; when determining if two programs are identical, compare their semantic output or hash them independently. Tree-shaking is conservative: function names appearing in comments may cause a function to be retained unnecessarily, which only affects binary size and does not impact correctness. If function pointer tables or runtime symbols assembled via macro concatenation are introduced in the future, such symbols must be explicitly added to the root set (this constraint is documented in ADR-38).

**On-Demand Inclusion of System Headers (ADR-39)**: `<windows.h>` resides within the `#ifdef _WIN32` branch, but because it belongs to "non-function text that must be preserved verbatim", function closure pruning cannot remove it—following ADR-38, a program consisting solely of `print(1)` would still pay about half a second parsing the entire suite of Win32 declarations. Now, each runtime function **depending on declarations from windows.h** (such as the 16 functions including `ae_widen`, `ae_try_cwd`, `ae_now_ms`, and `ae_run_command`) is tagged with `/* win32-header */` at its definition; this tag is retained or deleted alongside the function unit, so if the pruned runtime leaves zero such tags, the compiler replaces `#include <windows.h>` with a single-line comment. Programs utilizing files, paths, directories, clocks, environment variables, working directories, or child processes retain this header and `WIN32_LEAN_AND_MEAN` as usual; purely computational, vector, string, floating-point, and JSON programs no longer pay this cost.

This determination is based on **capabilities used by the program** rather than the platform: the generated C text is identical on both platforms, and Linux does not preprocess Windows branches anyway, so the benefits are primarily realized on Windows. The consequence of omitting a tag is that the generated C lacks declarations and triggers a direct compilation error (failing explicitly); the consequence of adding an extra tag is merely parsing a header one extra time; neither silently alters runtime results. Hand-written minimal Win32 declarations (Design Document §21 W6) remain unimplemented, thus introducing no new ABI assumptions; neither `deps` nor cache keys participate in this decision, which occurs entirely during the C generation pruning stage.

## Counting Built-in `map_inc`

`map_inc(m, key, delta) -> i64` performs a counting operation in a single lookup: it adds `delta` to the value of `key` and returns the new value, defaulting to 0 for missing keys (with insertion). Unlike `map_get`, a missing key **does not return an Err**—absence yielding zero is part of the increment semantics. `m` is restricted to map variables or their fields, and moved maps are rejected; `delta` must be an `i64`. Hit keys are zero-copy. The histogram pattern (`bench/map.ae`'s get + match + store) thus converges into a single invocation; the return value is an expression and cannot be discarded as a bare statement.

## Traits and Implementations (trait/impl)

`trait Name { fn method(first: T, ...) -> R; }` declares a set of capabilities (ADR-47): the type parameter is strictly spelled `T`, the first parameter of a method must be `T` by value, remaining parameters and return types can be either `T` or concrete types, and method bodies are omitted; each method accepts at most 8 parameters, and each program supports at most 64 traits. `impl Name for Type { fn method(...) -> R { body } }` provides all methods for a concrete type, where signatures must match point-for-point (`T` replaced by the concrete type); method bodies are standard function bodies checked for ownership and deallocation according to regular function rules.

After introducing a trait bound on a generic function via `[T: Name]`, the function body can directly invoke methods belonging to that trait—**dispatch is resolved at instantiation time**: concrete argument types for T determine a unique `impl` method, and the invocation emits that exact function call (static dispatch, equivalent to a hand-written function call, with no method tables or function pointers). Bounds can be mixed with built-in bounds (`T: Add + Area`); trait methods with identical names can only be declared by **a single** constrained parameter, otherwise the call reports `method 'x' is ambiguous`. If a given argument type lacks an `impl` during instantiation, it reports `no impl of trait 'X' for 'Y'; required by 'Z'`.

**There is only one calling form**: when writing the trait into a generic body with constraints, call it as a standard function `method(value, ...)` (without the trait name or dot notation). Trait methods cannot be called outside of generic bodies; the method body of an `impl` is a standard function body containing no constrained parameters, so `impl` methods **cannot call each other**—please implement shared logic as standard functions. (Inherent methods, in the next section, are a different mechanism: registered per `(type, name)` and called as `value.name(...)`; nothing here applies to them.) Since `impl` function bodies are not registered by method name, they cannot be called directly, nor will they conflict with standard functions.

Consistency rules: `impl` blocks can only be written in the file where the trait or the type is declared (third-party files are rejected); each (trait, type) pair is unique per program; a maximum of 256 `impl` blocks are allowed per program. `pub trait` can be referenced by other files; an `impl` is registered as soon as its containing file is loaded via `use` (registration occurs upon loading, without needing to call any items from it).

v1 boundaries: Trait signatures do not support `&T` (the landing shape for borrows requires independent design); generic `impl` blocks (`impl Area for Pair[K, V]`), default method bodies, dynamic dispatch/trait objects, associated types, and `where` clauses are not supported. Missing `impl` blocks trigger errors at the instantiation site, not via pre-checks at the declaration site. See `examples/traits.ae`.

## Inherent Methods (`impl Type`) (ADR-0182)

`impl Type { fn name(self, ...) -> R { body } }` attaches methods to a concrete struct **or enum** declared in the same file, and `value.name(args)` calls one; `impl Type { fn name(...) -> R { body } }` declares an associated function, called as `Type::name(args)` (ADR-0186). Scope: concrete types only, `impl` must follow the type's declaration, at most 8 parameters per method, at most 256 methods per program, and generic types are excluded (`impl Pair[K, V]` is rejected).

**Internal shape**: a method is an ordinary function whose parameter 0 is the receiver, and `value.name(args)` is that function called with `value` first. The runtime and the backend are unchanged — no method table, no function pointer, no indirection; dispatch follows the receiver's static type and is resolved at compile time.

**Receiver semantics (ADR-0182, ADR-0184)**: `self` is a by-value parameter, so calling a by-value method on an owned value **moves** it; `c.value(); c.value();` fails for the same reason `f(c); f(c);` does. `&self` declares a read-only receiver: the struct can now be borrowed, and `value.m(...)` **auto-borrows** the receiver for the call — the caller keeps ownership, the same variable can be called on again, and shared logic reaches itself through `self.other()` when `other` also declares `&self`. The borrowed receiver must be a bare struct variable (or an existing `&Type`, which forwards its pointer); a temporary or a struct field is rejected with a message that says to bind it first. `&mut self` declares an **exclusive mutable receiver** (ADR-0185): the body writes fields through the pointer (`self.n = self.n + 1;`), the caller must own a `var` binding, and nothing else may borrow the struct during the call. A `&mut self` method reaches a `&self` method through the same borrow (reading shrinks freely); a `&self` method cannot call a `&mut self` one. A `&self` or by-value receiver still keeps the caller's ownership rules.

**Associated functions** live in the same block: a function declared without a receiver is reached through the type name, `Point::new(3, 4)`, which is where constructors belong. The two forms are told apart by the declaration, not by the call, so `value.new(...)` on an associated function and `Point::get()` on a receiver method are both errors that name the correct form (ADR-0183). `::` therefore has two meanings, and the receiver's own declaration decides which: `Enum::Variant` for enum variants, `Type::name` for an associated function. Nothing is resolved by guessing at the call site.

`self` is a parameter name rather than a keyword: it is recognized only as the first parameter inside an inherent `impl` block, and anywhere else reports that it is only available there. `pub` is accepted before a method and changes nothing — a method is exactly as visible as the type it belongs to. Trait methods (previous section) remain a separate mechanism: they dispatch through generic bounds and are called with plain function syntax.

Rejected at declaration: a method named `main`; a built-in name (`len`, `push`, ...); a name that repeats a field of the type, because `value.name` would then have to mean two things; a duplicate method on the same type; an `impl` naming something that is not a struct, or a struct declared in another file.

**Enum methods (ADR-0186)**: the receiver is an owned enum, so `value.area()` moves it exactly as passing the enum to a function would — one binding per call. Inside the body, `match self { Shape::Circle(r) => ... }` reads payloads through the usual binding rules (views, no moves). `&self`/`&mut self` on enums are rejected in this version. `::` on an enum stays shallow: the name after it decides — a variant name is a variant path (`Shape::Circle(2)`), anything else reaches the impl's associated functions (`Shape::circle(2)`).

**`Self` (ADR-0186)**: inside any impl block — inherent or trait — `Self` stands for the impl's own type. Three forms: `-> Self` in a signature (the constructor's return type), `Self { ... }` (a struct literal of the impl's type), and `Self::name(...)` (an associated function of the impl's type, which is how a method delegates to its constructor). Outside an impl block, `Self` is rejected in both type and expression position.

**Generic impl blocks (ADR-0187)**: `impl Pair[K, V] { fn new(k: K, v: V) -> Self { ... } }` declares a method template for a generic struct. Each (method, argument list) pair instantiates its own function — signatures included, so `V` may appear anywhere a type can (`Option[V]` nests). `Self` is the instantiation; associated functions (`Pair[string, i64]::new(...)`) work and chain into method calls. One impl per generic struct, in the declaring file; no constraints on the parameters yet (a constrained generic function is the workaround for \-shaped needs). Receiver rules are the concrete ones per instantiation.

Known gaps: associated functions on generic structs via trait impls (`impl Show for Pair[K, V]`), bounds on impl parameters, borrowed enum receivers, and method calls on a struct-typed field of a variable (`plot.origin.distance()` is rejected — auto-borrow does not have a place-form for fields yet; compute from the field's scalar members instead). See `examples/methods.ae`, `examples/struct_borrow.ae`, `examples/enum_methods.ae`, `examples/generic_impl.ae`, `examples/closures.ae`, and `examples/function_types.ae`.

## Mutable Struct Borrows (`&mut Type`) (ADR-0185)

The exclusive mutable borrow: a parameter `fn bump(c: &mut Counter) -> i64` or the receiver `&mut self`. The callee **writes fields through the pointer** (`c.n = c.n + 1;`) for the duration of the call; the caller keeps ownership and regains every right when the call returns.

**Rules**: the lender must be a `var`-declared bare struct variable; the call site spells `bump(&mut c)`; while the call runs, no other borrow (shared or mutable) of that struct may be taken in the same statement; a borrow cannot be upgraded from `&Type` to `&mut Type` (a `&self` method cannot call a `&mut self` method), but a `&mut` borrow freely forwards as a pointer for `&Type` parameters and receivers. A `&mut` slot is writable without `var` — writing is its purpose. Whole-struct assignment through a borrow (`c = Counter { ... }`) and map-field writes through one are rejected with named workarounds. Like every borrow, it cannot be stored or returned.

**Interaction with string views (M2.5)**: a `&mut` lending call is a release site — the callee may write any field, so it releases the viewed bytes of the lent struct at the call point. When the only active borrows of the base are persistent string views, the conflict is decided by the NLL regions, not on sight: a call after the view's last use is allowed (`print(head); d.rename("beta");` parses), while a call the view may still be read after is rejected with `cannot mutate 'd' while a view binding of it may still be read`. The language pins left-to-right evaluation, so within one statement a view read *before* the call sees the bytes intact and a read *after* the call is the same rejection. Same-statement call-argument or `&mut` borrows keep the on-sight rejection (`c.doubled() + c.inc()` stays rejected).

## Closures (ADR-0188)

A closure literal is `|a: i64, b: i64| -> R { body }` (`||` for no parameters); parameter and return annotations are required, and the body must return on every path. A closure compiles to an ordinary function whose leading parameters are its captures, so calling one is a plain call:

- **Read-only captures borrow**: a body that only reads a `string`, `vec`, or `struct` captures it as a view/`&T` — the closure is callable any number of times, and the outer variable cannot move or be written while the closure name is live.
- **Consumed captures travel by value**: a body that needs ownership (`return note;` hands the capture over) makes every capture a value capture — each call moves the outer variable, so a second call is a use-after-move error.
- **Scalars always copy.** Maps travel by value (they cannot be borrowed).
- Mutating a captured container or field is rejected: writes would hit a copy. A closure has no storage, so it cannot be returned or stored, and closures nest.

## Function Types (`fn(T) -> R`) (ADR-0189)

A parameter written `fn apply(f: fn(i64) -> i64, x: i64) -> i64` accepts a **function value**. Pass a function parameter with the same signature, a non-capturing closure literal, or a local binding of such a closure. A capturing closure needs an environment and is rejected in this position. Inside the callee, `f(x)` calls through the pointer the caller passed. Function types and closure parameters also accept read-only string, vector, structure, and fixed-length array borrows. For example, use `fn(&string) -> i64` and `|text: &string| -> i64 { return len(text); }`. An owned temporary passed as a string view is released after the call. Supported vector borrows are `&vec`, `&vec[string]`, and `&vec[f64]`. A callable can also combine `&Pair` and `&[i64; 2]` parameters. The caller retains ownership of each borrowed value. Function values can also take an exclusive structure borrow such as `fn(&mut Pair) -> i64`. An indirect call can mutate the borrowed structure, so any existing view that may be used after the call prevents the borrow. Identical signatures intern to one type, so two closures of the same shape are interchangeable. A visible, safe ae function with a matching signature can be passed by name, as in `apply(double, 5)`. The function name is resolved in argument position. Function values cannot yet be returned or stored in fields.

## Struct Borrows (`&Type`) (ADR-0184)

A user struct can be borrowed read-only: a parameter written `fn area(r: &Rect) -> i64` (including a generic instantiation, `&Pair[string, i64]`), or the receiver `&self` of a method. The callee reads fields through a pointer — `r.w`, `r.origin.x` — and an owned field read (`r.label`) works wherever a read-only string works: `count_lines_with(r.label, "e")`, `r.label + "!"`, views. Nothing is moved and nothing is copied.

**Call sites**: pass a bare struct variable with an explicit `&` — `area(&r)` — exactly like the container borrows; forwarding a borrow parameter uses `inner(&r)` as well, which passes the pointer along unchanged. A `&self` method is called **without** the `&` (`plot.area()`), since the receiver form already says the call borrows.

**Borrow lifetime**: a call-argument borrow ends with the statement that made the call — the callee has returned by then and nothing retains the pointer — so `print(plot.area()); plot.w = 40;` is legal. The persistent borrows (string views, token cursors, `for`-in containers, `match` subjects) keep their existing until-scope-end rule. While any borrow is live the struct cannot be moved, written (`r.w = 40;`, `r.label = "x";`), reassigned, or mutated through its fields; borrowing a moved variable is rejected.

**What is not allowed**: storing a borrow in a variable (`let alias = r;` — borrows exist only as parameters and call arguments); returning one (`-> &Type` is rejected for functions and methods alike — a borrow of a parameter would outlive the callee's frame); assigning to or writing through a borrow parameter; borrowing a temporary or a struct field. The receiver-by-value rule and the field move rule are unchanged. See `tests/run/struct_borrow.ae` and `examples/struct_borrow.ae`.

## String Vectors

`split(s, sep) -> vec[string]` splits by a delimiter (retains empty segments, Python semantics; an empty delimiter is a runtime error); `join(parts, sep) -> string` joins with a delimiter (borrows the vector, performs total length overflow check first); `args() -> vec[string]` returns program arguments (including `argv[0]`). **Arguments are always UTF-8**: Windows CRT passes the command line to `main` according to the ANSI code page, so `args()` converts it from UTF-16 to UTF-8 at the entry point (ADR-54). Consequently, Chinese paths passed via the command line can be used directly in file APIs; characters that cannot be represented by the code page are lost before entering the program, which is not something `args()` can recover. The type is written as `vec[string]` (`vec` alone denotes a vector of `i64`). `vec[string]` is an owning container: assignment/passing/returning moves the container; `push` moves in a string, `pop` releases and removes the last element; `v[i]` reads and `v[i] = s;` writes perform boundary checks based on the current length (writes check the index first, release the old element, then move in the new value). **Elements are read-only borrows**: elements cannot be moved out of the vector (splicing or assigning to a new variable is rejected); `len(v)` is O(1). `split`, `args`, `join`, `lines`, `count_lines_with`, and `tokenize` are reserved names. The result vectors of `split` and `lines` place all tokens into a single byte area (ADR-49): the number of allocations for a single split is independent of the number of tokens, and elements remain read-only borrows that cannot be moved out; vectors produced by `push`, `args`, and `keys` remain element-wise owned. `lines(s) -> vec[string]` splits by newlines: trailing newlines do not produce an empty line at the end, internal empty lines are preserved, and empty input results in zero lines (newline scanning is implemented with runtime word-size optimization). `count_lines_with(text, pattern) -> i64` counts lines containing the pattern: a single-pass, zero-allocation fused implementation; empty text results in zero, and an empty pattern matches every line.

**`vec[f64]` (ADR-61)**: An owning vector of `f64` elements, isomorphic to `vec` (`i64`)—assignment/passing/returning moves the vector, and it is released when the scope exits or returns early; `v[i]` reads and `v[i] = x;` writes perform boundary checks based on the current length, and elements are pure values (no borrowed elements, can be overwritten entirely). Literals are inferred based on element type: `vec[1, 2]` is `vec`, `vec[1.0, 2.0]` is `vec[f64]`, and **mixed elements trigger an immediate error** (no implicit conversion is performed); an empty literal `vec[]` remains `vec`; an empty `vec[f64]` is created using `f64vec_new()` (aligned with `strvec_new`), and `push`/`pop` accept `f64`. In `for x in v`, `x` is a copy of the `f64`; `&vec[f64]` is a read-only borrow, which can be used as an argument and as a generic `&T` argument; struct fields and enum payloads can use `vec[f64]` and are released exactly once along with the owning value. **`sort`/`reverse` are not supported for `vec[f64]`**: NaN values lack a total ordering, and a comparator cannot be both fast and platform-independent; this is explicitly rejected rather than providing platform-dependent ordering. C generation stores f64 elements in the shared `ae_gvec` header (8-byte elements, no drop routine) — the same generic vector every non-string element type uses (ADR-0235). See `examples/float_stats.ae` for examples.

**Generic element types (P2.4, ADR-0235)**: a vector's element type is part of its type. `vec[T]` accepts any scalar, `bool`/`char`, a function or raw-pointer value, a `#[derive(Copy)]` struct or enum, an owned struct, `string` (the `ae_strvec` family), or a nested vector (`vec[vec]`, `vec[vec[f64]]`). A vector literal infers `T` from its elements and rejects mixed elements (`vec[1, vec[2]]` is an error); an empty literal still defaults to `i64`. A vector of an owned element (`vec[vec]`, `vec[MyStruct]`) stores the element bytes and releases each element exactly once on `pop`, on overwrite (`v[i] = x;`) and at scope exit, through the `ae_gvec` header's drop hook (a struct element's own `Drop` runs first, then its fields release). `push(v, x)` and `v[i] = x;` **move** an owned value in — a field, a vector element view, or the container itself cannot be moved into it — and `v[i]` of an owned element is a read-only view (`&vec` for a nested vector, `&Struct` for an owned struct): binding it to a local is rejected ("cannot store a borrowed vector/struct in a variable"), `push(v[i], …)` is rejected, fields read inline (`items[0].name`), and `for row in rows` binds the element as the view so it can be read or forwarded to a `&T` parameter by name. A borrow argument may name a binding (`&name`) or **one vector element** (`&items[0]`, `&items[len(items) - 1]`): the element is addressed in place and passed to a `&Struct`/`&vec` parameter for the duration of the call, so a call can read an owned element (or a nested vector) without moving or copying it. The borrow is read-only (`&mut items[0]` is rejected) and ends with the call — a later `push`/`store` on the vector is allowed. A borrow argument also names a **place inside a binding**: a struct field (`&h.item`, nested `&o.inner`), a vector field (`&r.cells`), or an element of a vector field (`&t.rows[0]`) — the place is addressed in place, the borrow is read-only (`&mut h.item` is rejected) and ends with the call, and the root binding must be live and not moved (`struct 'H' has no field …`, `only a struct has fields, found string`). **String literals** work again: `vec["alpha", "beta"]` is a `vec[string]` — a text literal is an owned element, an owned string variable moves in, and a string view (a struct field read such as `vec[p.name]`, a `slice_view`, a string-vector element) is copied into the vector, so `push(v, p.name)` never aliases the field. Owned **enum** elements remain unsupported. `vec[vec]`/`vec[MyStruct]` use one runtime header (`ae_gvec`) with a per-element drop thunk; the generated C carries only the thunks the program names. A struct's vector **field** indexes through the receiver (`r.cells[0]`, `len(r.cells)`, also inside a `&Struct` function where `w.cells[i]` reads through the borrow); for every family the read goes through the field's lvalue, and a string or owned element read keeps the struct variable borrowed while a binding can still read the view (`let s = w.words[0];` then `w = …` is rejected). **Slices (`&[T]`, ADR-0236)**: a read-only borrow of contiguous elements — `fn sum(values: &[i64]) -> i64`. A call passes `&v` (a whole vector binding whose element is `T`), `&arr` (a whole array binding), or a slice parameter by name; the slice value carries the runtime length. `len(values)`, `values[i]` (bounds-checked; the vector's element read rules apply — Copy values, `string` views, `&vec`/`&Struct` for owned elements) and `for x in values` all work, including a slice of nested vectors (`&[vec]`) and of owned structs (`&[Tagged]`, where `items[0].name` reads fields). A slice argument names a whole binding: `&v[0]` (an element slice) is rejected, as are writing through a slice (`push(values, …)` says "push expects a vec, found &[i64]"), binding one to a local, and returning one. **Sub-slices** (`&v[start..end]`, ADR-0236 rung 3) window a vector, an array or an existing slice parameter: both bounds are i64 expressions evaluated at the call site, the window keeps the element size and starts at the offset, so `len`/index/`for` read only the visible range (`&v[1..3]`, `&a[0..2]`, `&values[1..len(values)]`, and a window of a slice parameter forwarded onward). A range with a missing bound (`&v[1..]`), a non-integer bound, a mutable range (`&mut v[0..1]`), a field receiver (`&r.cells[0..1]`), an element slice (`&v[0]`) and a moved source are rejected; an out-of-range window (`start > end` or `end > len`) is a runtime trap at the call site ("slice range out of bounds") with the same message and position on the compiled and interpreted paths. A borrow argument may also name **one element of a slice parameter** (`&items[0]`, `&rows[len(rows) - 1]` inside `fn f(items: &[Tag])`): the element is addressed in place and passed to a `&Struct`/`&vec` parameter for the call's duration, exactly like the vector element borrow (a `string` element is not a place-borrow target, same as the vector form). A slice parameter may use a **generic element** (`fn size[T](v: &[T]) -> i64`): each call instantiates it by spelling its type arguments (`size[i64](&ints)`, `size[string](&words)`; inference is P2.5.2), and `len`/`for`/sub-windows work for every instantiation. `&mut [T]` is a later rung.

**Writing through a field receiver** works for a `var` struct or a `&mut` root: `push(r.cells, x)`, `pop(r.cells)`, `sort(r.cells)`/`reverse(r.cells)` and `r.cells[i] = x` address the field lvalue (a `&mut` root writes through its pointer, `h->cells`), release a replaced/popped owned element exactly once, and keep the same rules as their binding forms (mutable root, element type, a live element view blocks the write, a moved root is rejected, a non-vector field is `push expects a vec, found …`). The receiver may be a **nested chain** (`a.b.c.cells[i] = x`, `push(a.b.c.cells, x)`, `len(a.b.c.cells)`), resolved field by field from the root binding; a missing field names its struct. Nested **field stores** work too: `o.m.inner.n = 5` (scalar), `o.m.inner.name = "beta"` (string), `o.m.inner.cells = vec[7, 8]` (container, the old value releases first) and compound forms (`o.m.inner.n += 3`, also through a `&mut` parameter), with the same rules as a one-level store — the root must be mutable and must not have been moved (writing into a moved value is rejected like reading it). A nested *map* field store (`a.m.counts[k] = v`) is not supported yet. A `&Struct` (read-only) root cannot write its field.

## Borrowed String Views

`slice_view(s, start, end) -> string view` creates a zero-copy borrowed view. The base can be a **raw string variable** or a **string field of a struct variable** (`slice_view(p.name, 0, 5)`, ADR-52); the latter borrows the **entire variable**—the variable cannot be moved during the view's lifetime, and **writing to any of its fields** follows the same last-use rule as a whole-variable write: the write is rejected while the view can still be read later (`cannot modify '...' while a view binding of it may still be read`) and allowed once the view is dead — still variable-granularity, not field-level borrowing. Since M2.5 L1 (ADR-0205), the view's lifetime ends at its **last read** rather than at the scope's end: a whole-variable assignment after the view's last use is allowed (the write releases the old bytes; a view created after the write reads the new ones), while a write the view can still outlive—any read of the view on a later path—is rejected with `cannot assign to '...' while a view binding of it may still be read`. Moving the base is flow-sensitive the same way: after the view's last use, `let t = s;` is allowed (the buffer moves to `t`); while the view can still be read later, it is rejected with `cannot move '...' while a view binding of it may still be read`. Nested fields (`a.b.c`), fields on array/vector elements (`v[0].name`), and non-string fields are still rejected, each with its own error message. Views are non-owning types: assignment/passing copies the borrow, and they are never released. **A view binds once** (M2.5 slice 4, ADR-0205): a view binding is immutable — `var h = slice_view(...)` is rejected at the declaration ("a view binding cannot be mutable; declare it with 'let'"), and assigning into a view slot (`h = slice_view(...)`) is rejected ("a view binding cannot be reassigned; declare a new view with 'let'"). The token cursor's base is covered by the same rule. The NLL regions treat view slots as declare-only, so a reassigned view — which would re-point the view at different bytes with no kill in the region math — cannot exist. Views support `len` (O(1)), `contains`, `==`/`!=` (by content), `print`, `bytes`, `slice` (obtains an owning copy), and `slice_view` (re-borrowing); they **can be concatenated with strings** (`+` copies the view into a new string, while the view itself remains usable); they cannot be used as function return types (no cross-function lifetime tracking), nor can they be passed as `string` to functions receiving by value. Out-of-bounds views report runtime errors with location information. `for x in vec[string]` iterates over elements as borrowed views (elements cannot be moved out, and the container cannot be modified/moved within the loop).

## Streaming Token Cursor `tokenize`

`tokenize(text, sep) -> token cursor` produces a stream of tokens using the **same set of boundary rules** as `split`, but yields only one read-only view at a time without materializing a vector: text with 450,000 tokens does not allocate memory per token (ADR-53).

- **The base must be storage**: a raw string variable or a string field of a struct variable. The cursor borrows the **entire variable** (same rule as `slice_view`, including the M2.5 L1 last-use lifetime for whole-variable writes): the variable cannot be moved during the cursor's lifetime, and writing to any of its fields is rejected. Temporary values (concatenation results, function return values) are rejected because they would be released before the first iteration.
- **Only `for` consumes the cursor**, and it must be bound to a raw variable first:

  ```ae
  let text = read_file(path);
  let cur = tokenize(text, " ");
  for token in cur { total = total + len(token); }
  ```

  Each `for` loop restarts from the first token, and keeps its own position. Sequential and nested loops can reuse the same binding.
- **No `len`**: counting requires consuming the entire stream, which is exactly what the cursor aims to avoid; use `split` when counting is needed. Cursors cannot be used with `print`, stored in vectors or structs, or used as return values or arguments (type mismatches will trigger respective errors).
- **The delimiter is copied into the cursor**, so temporary values can be passed (`tokenize(text, " ")`); the capacity is 16 bytes, and both empty delimiters and overly long delimiters trigger runtime errors at the call site.
- **Elements are views**: if you want to retain a token, use `push(v, token)` (explicit copy); otherwise, it becomes invalid along with the base string after the iteration ends.

The boundaries match `split` precisely: trailing delimiters preserve trailing empty segments, consecutive delimiters produce empty segments, empty inputs produce a single empty token, and multi-byte delimiters follow non-overlapping matching. For examples, see `examples/tokens.ae`; for the benchmark program, see `bench/textlazy.ae`.

## Modules and Visibility

`use "lib.ae";` can only appear at the top of a file (only comments may precede `use`). Paths are resolved relative to **the directory containing the current file**, so when importing a module within a directory, its own `use` statements are also resolved relative to its own location. Loading is depth-first, identifying identical files via normalized filesystem paths; a fully loaded file is loaded only once. If a file imports a file currently pending in the active loading chain, a cyclic import is reported. Therefore, duplicate imports and diamond dependencies are permitted, while true recursive dependencies result in an error. `main` is unique across the entire program, and library files do not require `main`.

Top-level items are private by default: only `fn`, `struct`, or `enum` declarations marked with `pub` can be used by other files (`pub` may also precede `enum` or `struct`). A file can always see its own private items, and preset result enums are public to all files. Name collisions across files still consistently result in errors (file-isolated private namespaces are not yet implemented, see limitations), meaning private items also cannot conflict with names in other files.

Two related checks: using an unexported name reports `function 'x' is private to <file> (mark it 'pub' to export it)` (the same applies to structs and enums). If a `pub` function's parameter or return type is a private type local to the file, an error is reported **at the definition site**: `public function 'x' exposes private struct 'Y'`, rather than waiting for every call site to hit a wall.

## Interface Summary and Dependency Graph

`ae deps <source.ae>` lists each module in loading order, its `uses` dependencies, the count of public interface entries for that module, and its summary hash, concluding with the program-wide fingerprint. The summary consists solely of `pub` function signatures, `pub` struct/enum shapes, and generic declarations: function bodies, private items, comments, and local variables do not participate. Therefore, **modifying only function bodies leaves all hashes unchanged, while modifying a `pub` signature changes the corresponding module and program-wide fingerprints**—precisely the decision basis needed in the future for "modifying an implementation without rebuilding unrelated packages."

Currently, it is **merely a diagnostic and planning tool and does not participate in any caching decisions**: the backend still utilizes a single translation unit per program, so modifying a function body will still recompile part of the program (though it no longer compiles the full runtime, as noted above). Path labels uniformly use `/` to facilitate cross-platform comparison, but do not fold case; case-sensitivity differences between Windows and Linux remain known platform discrepancies. `deps` fully loads and checks the program, and syntax or type errors will be reported just like in `check`.

## Structs

`struct Point { x: i64, y: i64 }` defines a sequence of named fields; field types can be any registered type (scalars, strings, vecs, or other structs). Self-reference is structurally impossible (the struct name is not yet registered within its own body), so infinitely-sized layouts do not exist. Constructing `Point { x: 1, y: 2 }`: fields can be written in any order, but each must appear exactly once; missing, duplicate, or unknown fields are rejected, and field expressions are evaluated in declaration order. Field access via suffix `p.x`: scalar fields are copied immediately (subsequent deallocations do not affect the copy), while owned fields (strings, vecs, or structs) are **read-only borrows**—fields can never be moved out of a struct. Field assignment `p.x = value;` requires a mutable variable and deallocates the old owned value prior to overwriting. Whole-struct assignment `p = expression;` follows move semantics: the old value is deallocated first. A struct owns all its fields: assignment, parameter passing, and returning move the entire struct. Scope exits, early returns, and jump paths clean up resources using type-generated destruction routines, ensuring zero leaks and no double frees. Post-move usage is rejected by the compile-time move set (structs have no runtime sentinels; compile-time checks serve as their safeguard, as documented accurately). Struct names cannot be used as variable names; built-in reserved names likewise cannot serve as top-level conflicts outside of struct/field names.
**`#[repr(C)]` and the layout query pair (M2.12)**: `#[repr(C)]` before a concrete `struct` fixes its layout to the C rules — declaration order, each field at its natural alignment, struct alignment the maximum field alignment, size rounded up with trailing padding. The attribute is rejected on generic structs (no single layout until instantiated) and on structs with owned fields (the C side cannot honor their release logic); nested `#[repr(C)]` structs are legal. A `#[repr(C)]` struct may cross an `extern "C"` boundary by value — scalars, `*const T`/`*mut T`, and `#[repr(C)]` structs are the legal shapes; anything else is rejected at the declaration. The layout is pinned by the compile-time queries `c_size_of[Pair]()` (byte count, trailing padding included) and `c_offset_of[Pair]("field")` (the field's byte offset), evaluated to constants in the parser; both require the attribute, since without it the layout is the compiler's choice. The compiler also emits a real C prototype for every `extern "C"` declaration, so a foreign symbol works whether or not its definition precedes the call.

## Raw Pointers and `unsafe` (M2.12, ADR-0207)

The unchecked corner is explicit at every boundary; safe code's guarantees (ownership, borrows, bounds, checked arithmetic, initialization) hold unchanged, and `unsafe` never disables a check on code the checker can prove. The full rule set and test matrix live in `spec/unsafe.md`.

**`unsafe` blocks and `unsafe fn`**: `unsafe { ... }` is a scoping container — inner statements run inline, locals bind and die inside it. Dereferencing a raw pointer (`p.deref()`) and calling an `unsafe fn` or an `extern "C"` declaration require the block (E0700 / E0701); a block containing no unchecked operation warns `unnecessary unsafe` (W0702, advisory — compilation succeeds). Warning emission happens at parse time, so a warm frontend-cache hit (which skips parsing entirely) suppresses warnings — run-corpus files therefore keep their `unsafe` blocks non-decorative. An `unsafe fn` declaration requires a doc comment naming its preconditions (E0704); its body still needs an inner `unsafe {}` for unchecked operations (Rust-2024 style). Calls to an `unsafe fn` or a declared extern count as the unchecked operation the enclosing block legalizes.

**Raw pointers** `*const T` / `*mut T` are untracked addresses: creating one is safe, reading or writing through one is `unsafe`. They are copyable, comparable for equality, and carry no ownership — the move set and the borrow registry never see them. A pointer binds as a plain local; pointer type annotations are writable in `extern "C"` signatures (`-> *mut i64`) as of the ADR-0208 allocator bridge, and pointer types are otherwise born from casts:

```ae
fn main() {
    var n = 41;
    let p = &n as *const i64;      // borrow-as-pointer, safe
    unsafe { print(p.deref()); }   // read through the pointer
}
```

- The borrow-as-pointer cast takes the address of a **local variable** (`&expr as *const T`, `&mut expr as *mut T` — the mutable form requires a `var` binding); reinterpret casts between pointee types do not exist yet.
- A pointer to an **owned value is rejected at the declaration** (`&s as *const string`): the pointer's borrow is untracked, so safe code could dangle it by moving the value. Scalars are the current pointee surface; the interpreter's Moved-slot trap ("reading through a pointer to a moved value") is the armed backstop for when pointer-to-owned lands.
- `*mut T` writes use the pointer-store statement inside `unsafe`: `*p = value;` (the pointee must be non-owned). Reads go through `p.deref()`; a bare `*p` is not a read expression.
- Pointer arithmetic (ADR-0209 step A) lives inside `unsafe` too: `p.offset(n)` advances n **elements** (C's own scaling does the sizing), `p.byte_offset(n)` moves n **bytes** through `char*` and back; both keep the base's pointer type and reason about no bounds. The interpreter does not model address arithmetic — a program using it traps there and runs compiled (same story as extern calls).
- The layout queries resolve a type parameter through the instantiation's substitution table, so a generic body can ask `c_size_of[T]()` about its element — the piece `Vec[T]`'s allocation builds on.
- `extern "C"` declarations declare link-time C symbols (`extern "C" fn abs(v: i64) -> i64;`) and take real C prototypes; calling one requires `unsafe`. Argument and return types must be C-ABI-shaped: scalars, `*const T`/`*mut T`, and `#[repr(C)]` structs by value. `#[no_mangle] extern "C" fn name(...) { ... }` exposes an ae function as a C symbol; its body is safe code.
- `#[repr(C)]` pins a struct's layout (declaration order, natural alignment, trailing padding) and is required for any struct crossing the boundary by value; the compile-time queries `c_size_of[T]()` / `c_offset_of[T]("field")` pin the numbers.

## Recoverable Errors and Type Conversions

The program presets nine result enums (no import required, fixed variant order, numbered 0–8): `ReadResult{Ok(string), Err(string)}`, `WriteResult{Ok(i64), Err(string)}`, `IntResult{Ok(i64), Err(string)}`, `DirResult{Ok(vec[string]), Err(string)}`, `FileResult{Ok(i64, i64, bool), Err(string)}`, `StatusResult{Ok, Err(string)}`, `BoolResult{Ok(bool), Err(string)}`, `CommandResult{Ok(i64, string), Err(string)}`, and `FloatResult{Ok(f64), Err(string)}` (the 9th, ADR-65, appended at the end to preserve existing numbering). Layouts are emitted on-demand (ADR-66): only result types actually used by the program enter the generated C code. Fallible built-ins: `try_read_file(path) -> ReadResult`, `try_write_file(path, content) -> WriteResult` (success returns bytes written), `parse_int(text) -> IntResult`. Failures return the error description payload within `Err`, **without terminating the process**; `read_file`/`write_file` remain the unrecoverable versions that terminate upon failure. `parse_int` strictly follows decimal format: optional `+`/`-`, ASCII digits only, the entire string must be consumed, with positive and negative bounds at `9223372036854775807`/`-9223372036854775808` respectively, while all other cases result in `Err`. `to_string(i64) -> string` performs decimal formatting, forming a round-trip with `parse_int`.

Result values are ordinary enum values: they must first be bound with `let`, then unwrapped using `match` (`match` does not accept expression subjects). Error text varies with the platform's `strerror` localization, and programs should not rely on exact content. `try_read_file`/`try_write_file`/`try_list_dir`/`path_exists`/`path_is_dir`/`path_join`/`path_name`/`path_parent`/`try_file_info`/`try_copy_file`/`try_rename_path`/`try_remove_file`/`try_create_dir`/`try_remove_dir`/`parse_int`/`to_string`/`map_new`/`f64map_new`/`map_get`/`map_has`/`map_remove`/`keys`/`utf8_len`/`utf8_prefix`/`strvec_new`/`f64vec_new`/`run_command`, mathematical built-ins `sqrt`/`abs`/`floor`/`ceil`/`round`/`exp`/`log`/`sin`/`cos`/`pow`/`atan2` (ADR-60), and the eight result type names are all reserved words.

## Error and "Maybe" Propagation `?`

`let x = call()?;` and `call()?;` are propagation statements: when the result enum is in an `Err` state (or an Option is in a `None` state), all still-alive owned variables within the current function are deallocated first, and then the result value itself is returned to the caller. When in a success variant (`Ok`/`Some`), the `let` form extracts and binds the single payload (success variants must have exactly one payload), while the bare statement form deallocates the payload and continues execution. Bare statements are the language's only "expression statements" and **must end with `?`**, meaning there is no syntax for "silently discarding return values."

Propagatable types are one of two variant shapes, with fixed variant names and order: `{ Ok(...), Err(string) }` (all eight predefined result enums satisfy this, and custom enums with the same shape are also supported) or `{ Some(T), None }` (the predefined `Option[T]` satisfies this, and custom enums with the same shape are also supported). The success payload can be any owned type (`string`, `vec`, struct, enum); when the failure path is dropped, it is released according to the type's release routine. Propagation requires the outer function to return the **same** enum type; propagation cannot be used in `main`. A function can only propagate one family of results; crossing families (e.g., `DirResult` from `try_list_dir` and `StatusResult` from `try_copy_file`) must be handled via `match` at the boundary. `?` is a statement, not an expression, and cannot appear within larger expressions.

## Path Algebra and File Metadata

Path functions are pure string operations; they do not touch the file system and do not perform normalization (they do not resolve `.`/`..` or collapse redundant separators). `path_join(dir, name) -> string` inserts a `/` when necessary: if `dir` ends with a separator, they are joined directly; if `name` is an absolute path (starting with `/`, `\`, or a pattern like `C:`), it **replaces** `dir` entirely; if either argument is empty, it returns a copy of the other. `path_name(path) -> string` returns the last component (trailing empty separators are discarded first, so the name of `a/b/` is `b`; paths consisting only of separators return the separator itself). `path_parent(path) -> string` returns the part before the last component and removes redundant separators (the parent of `/a` is `/`); paths without separators have no parent and return an empty string rather than fabricating `.`. All output uses `/`: Windows accepts `/`, and both platforms print the same path text, ensuring tests and logs are comparable.

`try_file_info(path) -> FileResult` returns metadata: in `FileResult::Ok(size, modified, is_dir)`, `size` is the number of bytes (i64), `modified` is the **number of seconds since the Unix epoch** (Windows FILETIME is converted to this same standard), and `is_dir` indicates whether the path is a directory. If the path does not exist or access is denied, it returns `Err`; it **will not** silently succeed with a size of 0.

## File Organization Operations

All file system write operations return `StatusResult` (`Ok` without a payload, `Err(string)` with a reason) and will not terminate the process:

- `try_copy_file(from, to) -> StatusResult`: Copies content (64 KiB chunks); truncates and overwrites if the target exists; does not preserve permissions/timestamps (current limitation).
- `try_rename_path(from, to) -> StatusResult`: Moves within the same volume and overwrites existing target files (uses Windows `MoveFileExW` with `REPLACE_EXISTING`, and POSIX `rename`).
- `try_remove_file(path) -> StatusResult`: Deletes a file; **directories are strictly rejected** (POSIX `remove()` would delete empty directories; this is changed to check and report an error for consistency across platforms).
- `try_create_dir(path) -> StatusResult`: Creates all missing parent directories following `mkdir -p` semantics; existing directories are not considered an error.
- `try_remove_dir(path) -> StatusResult`: Deletes only empty directories and has **no** recursive deletion interface—silently deleting an entire tree is the easiest way to cause data loss.

By combining `for name in names` with these functions, one can write file organization workflows such as "list → check → move → clean"; see `examples/file_tidy.ae` for an example.

## Sorting, Clocks, and Environment Variables

`sort(v)` and `reverse(v)` reorder mutable vectors **in-place**: `i64` vectors are sorted in ascending numerical order, and `vec[string]` in byte-order (consistent with `keys()` and directory listings, ensuring output is identical across platforms). `vec[f64]` does not support these: NaN values lack a total ordering (ADR-61). Empty and single-element vectors are no-ops. `v` must be a `var` variable and cannot be called while it is being borrowed (e.g., inside a `for x in v` loop); to reverse, use `sort(v); reverse(v);`.

`now_s()` / `now_ms()` return the seconds/milliseconds since the Unix epoch (`i64`). `now_s()` uses the same units as the mtime in `try_file_info`, allowing direct subtraction to calculate "how long ago."

`env(name) -> ReadResult`: Returns `Ok(value)` if it exists, `Err("variable not set")` if it does not, and `Ok("")` if it **exists but is empty**—"empty" and "non-existent" are two different things; conflating them would cause `PATH=""` to silently become "no PATH." Empty names return `Err("variable name is empty")`. Environment variables are read-only: there is no `set_env`, nor is there an iterator.

`try_append_file(path, text) -> WriteResult` writes in append mode and returns the number of bytes; `try_write_file` still performs a full overwrite. Each call opens and closes the file; when writing many small lines, they should be concatenated into a single string and written at once. `sort`/`reverse`/`now_ms`/`now_s`/`env`/`try_append_file`/`set_cwd` are reserved names.

## Standard Input and Working Directory

`read_stdin() -> ReadResult` reads the **entire** standard input and returns raw bytes: returns `Ok("")` if the input is empty, and `Err(reason)` if reading fails. Content is not translated for line endings (on Windows, `stdin` is set to binary mode), so `a\r\nb` is read back as 4 bytes rather than 3—`len`, `bytes`, and `split` see the actual bytes on the disk/pipe. Reading does not validate UTF-8, consistent with `read_file`; `slice`/`utf8_*` still check boundaries based on code points. The entire input resides in memory; it is not suitable for massive streams.

```ae
fn main() {
    let input = read_stdin();
    match input {
        ReadResult::Ok(text) => { print(len(text)); print(utf8_len(text)); }
        ReadResult::Err(reason) => { print("cannot read: " + reason); exit(2); }
    }
}
```

`cwd() -> ReadResult` returns the absolute path of the current working directory, with separators unified to `/` (consistent with `path_join`/`path_parent`), which can be passed to `path_join` or the `try_*` series. `getcwd` can fail (directory deleted, permissions changed), so it returns a result rather than a raw string. It does not resolve symbolic links.

`set_cwd(path) -> StatusResult` changes the working directory for the **entire process**: all subsequent relative paths (including those in child processes started by `run_command`) are resolved relative to the new directory. There is no undo mechanism; to return to the original location, store the absolute path using `cwd()` first. If the target does not exist or access is denied, it returns `Err` and the directory remains unchanged—there is no "partially successful" state. This is a global side effect that cannot be expressed in the function signature, so it should only be used when explicitly intending to "enter a directory to perform operations"; prefer passing absolute paths whenever possible.

```ae
fn main() {
    let saved = cwd();
    let entered = set_cwd("out");
    match entered {
        StatusResult::Ok => { print("entered"); }
        StatusResult::Err(reason) => { print("cannot enter: " + reason); exit(1); }
    }
    // Relative paths here are all under out.
    let listing = try_list_dir(".");
    match listing {
        DirResult::Ok(names) => { print(len(names)); }
        DirResult::Err(reason) => { print(reason); }
    }
}
```

No `set_env`: `setenv` is POSIX-specific and invisible under `-std=c11 -pedantic-errors`, while injecting `_POSIX_C_SOURCE` would violate the constraint that "the exact same C code must compile on any strict C11 compiler" (see [ADR-25](decisions.md)). When a child process needs a different environment, it currently must be passed explicitly via commands (such as the `env` program).

`grep_cli.ae` and `pipe_stats.ae` are two acceptance examples: the former treats `-` as "read from standard input", while the latter computes pipeline bytes/characters/lines/longest line (`cat notes.txt | ae run examples/pipe_stats.ae`).

## Empty String Vectors and Child Process Execution

`strvec_new() -> vec[string]` constructs an empty `vec[string]`. `let v = vec[];` defaults to an `i64` vector when element types cannot be inferred, so string vectors initialized as empty and populated via individual `push` calls must start with this function.

`run_command(program, args) -> CommandResult` spawns a child process and waits for its termination: `program` is a `string`/view, and `args` must be a **bare `vec[string]` variable** that has not been moved (no copying, no taking views, borrowed during the call). On success, it returns `CommandResult::Ok(status, output)`, where `status` is the exit code and `output` is all text with stdout and stderr **combined** (no upper limit, reads until EOF). If the program fails to start altogether (file not found, missing execution permissions), it returns `Err(reason)`—this is the only case considered a "failure".

```ae
fn main() {
    let argv = args();
    var command = strvec_new();
    for i in 2..len(argv) { push(command, argv[i]); }
    let result = run_command("git", command);
    match result {
        CommandResult::Ok(status, output) => { print(status); print(output); }
        CommandResult::Err(reason) => { print("cannot start: " + reason); exit(1); }
    }
}
```

A non-zero exit code is **not** an `Err`: a child process exiting normally but reporting a failure is the same as your own program calling `exit(3)`. Mixing the two would make it impossible to distinguish between "the command failed to run" and "the command ran but failed". When killed by a signal, POSIX reports `128 + signal_number` (consistent with the shell's `$?`); Windows directly passes the exit code from `GetExitCodeProcess`.

Neither platform passes through a shell **implicitly**: `program` is executed directly, so on Windows, built-in commands like `echo` or `dir` require explicitly writing `run_command("cmd", ["/c", "echo", ...])`. Windows argument rules are derived from `CreateProcessW`'s quotation conventions, but intentionally leave conservative boundaries: quotes are added only to arguments containing spaces or tabs (adding quotes to every argument would cause `cmd` to treat the quotes as part of the command name), and arguments containing `"` or ending with `\` immediately return an `Err` rather than guessing—guessing `CreateProcess` escape rules incorrectly silently alters what the child process receives, which is far more dangerous than a startup failure.

The child process **inherits** the current standard input (identical on both platforms), so the content it reads competes for the exact same stream as your own calls to `read_stdin()`; whoever reads first gets it—to prevent the child process from consuming input entirely, pipe it to an empty file before launching this program. There are no other tunable options: environment variables, working directories, or timeouts cannot be set. Output is read into memory all at once, meaning long-running, high-throughput commands will exhaust memory; the current language does not yet support streaming processing. See `examples/run_tool.ae` for an example (forwarding its own arguments to a child process).

## JSON Path Queries

`json_get(text, path) -> ReadResult` retrieves a value by path: strings have their escapes decoded (including `\uXXXX` and surrogate pairs), numbers and `true`/`false`/`null` return raw text, and arrays and objects return raw slices. Paths are written as `key.sub[2].name`, an empty path represents the entire document, and `[0]` can be used directly on a root array.

`json_int(text, path) -> IntResult` accepts strictly pure integers (decimals or exponents cause an error, and `i64` overflow also errors); `json_bool(text, path) -> BoolResult` accepts only `true`/`false`; `json_len(text, path) -> IntResult` returns the number of array elements or object members; `json_has(text, path) -> bool` queries merely for existence (`null` is also considered existent).

```ae
fn port(config: &string) -> i64 {
    let found = json_int(config, "server.port");
    match found {
        IntResult::Ok(n) => { return n; }
        IntResult::Err(reason) => { print("no port: " + reason); return 8080; }
    }
}
```

The three types of failures are distinct: `no member named 'timeout'` (key missing), `'name' is a string, not a number` (key exists but type is incorrect), and `path segment [9] is past the end of the array` (out of bounds). Malformed paths themselves (`a.`, `a[`, `a..b`) are reported before scanning the document.

This is a **reader** rather than a validator: it checks syntax only along the path without verifying the entire document; numeric strictness is guaranteed only at the time of `json_int` conversion; duplicate keys take the first instance; fields whose key names contain `.` or `[` cannot be expressed via paths; there is no writing or serialization. Each call rescans the document. Configuration-level inputs are fast enough, but repeatedly querying the same field should extract and store it in a variable first.

## Hash Maps

`var counts = map_new();` creates an empty `map[string, i64]`; `f64map_new()` creates an empty `map[string, f64]` (ADR-65). Keys must be `string`s, and the value type is determined by the constructor and specified in the type (e.g., `map[string, i64]` / `map[string, f64]`, which can be used for variable annotations, parameters, return types, and struct fields).

- `counts[key] = n;` inserts or overwrites. Keys are **copied** by the runtime, so views (e.g., `&string` parameters, `vec[string]` elements) and temporary values can be used as keys directly; values are `i64` and do not involve ownership. The target must be a mutable map (a `var` variable or a map field of a mutable struct variable, e.g., `s.counts[key] = n;`), and it cannot be written to while borrowed.
- `map_get(m, key) -> IntResult`: Returns `Ok(n)` on a hit, or `Err("key not found")` on a miss—this allows "non-existence" to be distinguished from "a value of 0," unlike C-style APIs that use 0 as a sentinel for missing values. The reason text is a **shared read-only constant** (ADR-58): misses do not allocate memory, and the program can still treat it as a standard owned string for reading, comparison, concatenation, or copying into containers. The runtime identifies it by address during deallocation and skips it; its content, `len`, and comparison results are unremarkable.
- `map_has(m, key) -> bool`, `map_remove(m, key) -> bool` (returns whether the item was actually removed), `keys(m) -> vec[string]` (**copied** and sorted by byte order, ensuring consistent traversal order across platforms), and `len(m)` returns the number of entries.

**`map[string, f64]` (ADR-65)**: All built-ins above are generic across both map types, dispatched based on the value type—`map_get` returns `FloatResult` (the 9th predefined enum; the missing branch is the same read-only constant, zero-allocation on miss), `map_inc` increments and returns `f64`, while `keys`/`map_has`/`map_remove`/`len`/`m[key] = v` maintain the same shape with value types checked at compile time. Construction: `f64map_new()`; type notation: `map[string, f64]`. The runtime `ae_mapf_*` and `ae_map_*` are isomorphic (24-byte slots, parallel status bytes, half-load expansion, FNV-1a hashing with key-side implementation). See `examples/sensor_stats.ae` for examples.

Maps are owned values: assignment, pass-by-value, and `return` move the entire table. Scope exit and jump paths trigger type-generated release routines to reclaim all keys and the slot array, preventing leaks or double-frees. `map_get`/`map_has`/`map_remove`/`keys` only borrow the map during the call; the receiver must be a **bare map variable or its struct field** (e.g., `map_get(t.counts, k)`), not a more complex expression. Calls on moved maps are rejected at compile time, with `slots` null-pointer sentinels providing a runtime safety net.

Implementation uses open addressing + linear probing (FNV-1a hash, `AE_MAP_EMPTY/FULL/DELETED` tri-state, tombstones maintained for deletion to preserve probe chains; slots and status bytes are stored in two separate arrays, see ADR-57). When the load factor reaches 1/2, the map doubles in size and clears tombstones (ADR-56). Limitations: no direct `for k in m` traversal (please use `keys(m)`), value types are limited to `i64`, no custom hashing or capacity pre-allocation; `keys()` allocates a full copy.

## Enums and Pattern Matching

`enum Shape { Circle(i64), Rect(i64, i64), Empty }` declares an enum: variants can carry 0–16 positional payloads, with payload types limited to `i64`, `bool`, `string`, `vec`, and `vec[string]` (generic enums may also include type parameters; thus, enums cannot be self-contained, and recursive layouts do not exist). Variant names must be unique within an enum; conflicts between enum names and structs or built-ins trigger errors. Like structs, they must be declared before use within the same file. Construction: `Shape::Circle(3)`, `Shape::Rect(4, 5)`, `Shape::Empty`; the number of payloads must match the declaration, and `string` payloads are passed by move.

`match variable { Shape::Circle(r) => { ... } Shape::Rect(w, h) => { ... } Shape::Empty => { ... } }` is a statement: the subject must be a **bare enum variable**, and every variant must appear exactly once (exhaustiveness; missing a variant, duplicate matching, or incorrect enum names trigger errors). Wildcards and nested patterns are not supported. Branch bindings are read-only: `i64`/`bool` payloads are copied by value, `string` payloads are bound as `string view`, `vec` as `&vec`, and `vec[string]` as `&vec[string]`—none can be moved out of the enum. Views can be used with `len`/`contains`/`slice`/`==`/`print`/`+`, and borrowed vectors can be used with `len`/indexing/`for-in`/further borrowing. The subject is borrowed during matching: it cannot be moved or reassigned as a whole, though rebinding other variables is unaffected. `break`/`continue` within branch bodies apply to the innermost loop, not the `match`.

Enums are owned values: assignment, pass-by-value, and `return` move the entire enum. Use after move is rejected at compile time. Scope exit, early returns, and jump paths release payloads based on the current variant, ensuring `string` payloads are neither leaked nor double-freed. Assigning a new value to an enum variable releases the old payload before moving in the new one. Enums can be used as function parameters, return types, and struct fields. Enums cannot be `print`ed or compared as a whole.

## Generic Enums and `Option[T]`

`enum Either[T, U] { Left(T), Right(U), Both(T, U), Neither }` declares a generic enum: type parameters are written as `[T, U]` after the name, limited to single uppercase letters (`T`, `U`, `K`, `V`), with a maximum of 8. Payload types can be type parameters or fixed types. Generic **declarations** do not generate any layout; only instantiation does.

When using, type arguments must be specified: `Option[string]::Some("x")`, `Option[i64]::None`, `Either[string, i64]::Both("n", 3)`. Type arguments are limited to `i64`, `bool`, `string`, `vec`, and `vec[string]`—consistent with payload limitations, thus preventing recursive layouts. **A single argument list produces only one layout** (e.g., `Option[string]` is the same type everywhere and can be freely assigned, passed, or returned); different arguments result in different types (e.g., `Option[string]` and `Option[i64]` are not interchangeable, as their `Some` payload types differ).

`match` patterns use the **declaration name** rather than the instantiation name: values of both `Option[string]` and `Option[i64]` are matched using `Option::Some(v)` / `Option::None`, with the actual type of `v` determined by the type of the matched value (`string` payloads are still bound as views). Exhaustiveness, borrowing rules, and move semantics are identical to standard enums.

The predefined `Option[T] { Some(T), None }` is public to all files and represents "a value that may be absent": `fn locate(text: &string, needle: &string) -> Option[i64]` is much clearer than using `-1` or an empty string as a sentinel, as sentinels cannot be distinguished from a legitimate `-1` or an existing empty line. `?` works on `Option` as well: `None` is returned to the caller as-is, while `Some` binds the payload (see [ADR-21](decisions.md) and [ADR-34](decisions.md)).

Each program supports a maximum of 256 enum types (including built-in and fully instantiated ones), with an error reported at the instantiation site if exceeded; this is a code size budget, not a hard limit.

## Generic Structs

`struct Pair[K, V] { left: K, right: V }` declares a generic struct. The type parameter rules are identical to those of generic enums (single uppercase letter, maximum of 8, no duplicates). The declaration itself does not produce a layout; a concrete struct type is produced only upon instantiation, such as `Pair[string, i64] { left: "a", right: 1 }`.

- The same argument list produces only a single layout: `Pair[string, i64]` is the same type everywhere, can be assigned to each other, and can be passed to functions as the same parameter type. `Pair[i64, i64]` is a different type, and mixing them will result in a type mismatch error at the call site.
- Type arguments can be any nameable type: `i64`, `bool`, `string`, `vec`, `vec[string]`, `map[string, i64]`, another struct, an enum, or an instantiated generic (`Pair[string, Pair[string, string]]`). This is more lenient than generic enums—enum payloads only accept flat types because enums lack mutable layouts, whereas struct fields naturally allow nested structs.
- Field access, field assignment, moving, and dropping are identical to those of regular structs: owned fields can only be borrowed and cannot be moved out; `p.right = value;` drops the old value before overwriting, and the written field **owns** the value afterwards: an owned variable on the right side is consumed by the write (`p.a = s;` moves `s` — later uses of `s` are rejected; a field read on the right side is rejected as a field move — copy it with `slice` first), and exiting a scope generates `release` calls according to the instantiated field types.
- Recursive layouts do not exist: struct names are not yet registered within their own bodies, so `struct Node[T] { next: Node[T] }` reports an unknown type; the instantiation depth is therefore naturally limited.
- Each program supports a maximum of 256 struct types (including regular structs and all instantiations); `pub struct Pair[K, V]` can be imported by other files, and visibility rules are identical to those of regular structs.

## Generic Functions

`fn identity[T](x: T) -> T { return x; }` declares a generic function. The declaration itself does not produce any functions; call sites like `identity[i64](41)` produce a concrete function—the parameter types, return type, and function body are re-checked at that moment after substitution with the actual arguments.

- Type arguments must be explicitly written (`identity[i64](...)`); the language has no type inference, and omitting them triggers a prompt to add them. Mismatched argument counts or types both cause errors at the call site.
- Complete type checking of the function body occurs **after substitution**, so error messages originate from expressions at the declaration site (`'+' requires two strings`), pointing to the generic body itself rather than the call site. Constraints can intercept errors at two earlier points (argument shape checking at the call site, and capability pre-checks at the declaration site, see below), but **cannot replace** this check: ae has no capability proofs on unsubstituted generic ASTs, and the only way to guarantee correctness is to check each instantiation individually.
- The same argument list is instantiated only once (cached), so `identity[i64]` is the same C function everywhere; different arguments produce different functions.
- Within a generic body, type parameters can be passed further to other generics: `fn double_wrap[T](x: T) -> Option[T] { let inner = wrap[T](x); return inner; }`, where `Option[T]` and `Pair[T, i64]` are resolved according to the current substitution table.
- Declarations preserve their tokens and source code, making **cross-file instantiation** possible: with `pub fn identity[T](...)` in `lib.ae`, `main.ae` can directly call `identity[string](...)`. Instantiation treats the declaration file as the "current file," allowing generic bodies to call private functions and private types within the declaration file.
- Parameter types can be type parameters or borrowing forms `&T` (see the next section); `main` cannot be generic.
- Instantiating a function with the same arguments (directly or indirectly) infinitely expands itself, and the compiler reports an error at the cycle closure (`is already being instantiated with these type arguments`). Recursion with different arguments is permitted as long as it does not loop back to the same argument list.

## Generic Borrowed Parameters `&T`

`fn size_of[T](value: &T) -> i64 { return len(value); }` learns what `T` is **at each instantiation site**, so `&T` directly maps to the three existing read-only borrows without introducing new lifetimes, borrow kinds, or runtime type information:

| Type Argument | `&T` Instantiates To | Call Site Syntax | Available Inside Function Body |
|---|---|---|---|
| `string` | `string view` | `size_of[string](text)` | `len`, `contains`, `==`, `print`, `+` (copy) |
| `vec` | `&vec` | `size_of[vec](&numbers)` | `len`, indexing, `for x in v`, re-borrowing |
| `vec[string]` | `&vec[string]` | `size_of[vec[string]](&words)` | `len`, indexing (view), `for x in v`, re-borrowing |

The shape at the call site is determined by the **concrete type**, matching non-generic functions entirely: string views are passed directly, and vector borrows are explicitly written with `&`. All borrows do not move the arguments; original values remain readable and writable after the call completes. Inside the function body, access is read-only: views cannot be used as function return types, and borrowed vectors cannot be pushed to or written. `i64`, `bool`, structs, enums, maps, and arrays have no corresponding read-only borrows; instantiating `&T` with them reports `has no read-only borrow` at the instantiation site. Writing `&T` in a non-generic function reports `unsupported borrow type`. `&T` cannot be used as a return type, struct field, or enum payload, and constraints (`T: Add`) do not check borrowing capabilities—they remain solely for call-site argument shape checking (see the next section).

**A real limitation**: When instantiating another `&T` template within the same generic body, the call syntax varies with `T` (`string` does not write `&`, `vec` requires it), so such nesting is currently only reliable for the `string` shape; please separate other shapes by type in concrete functions. Uncalled generic declarations are not checked for `&T` at the declaration site, consistent with "function bodies are resolved only upon instantiation."

Incidentally, correcting a discrepancy between documentation and implementation: `&vec` / `&vec[string]` parameters **can now be re-borrowed** into another read-only parameter (`fn outer(v: &vec) { return inner(&v); }`), generating C code that directly passes the existing const pointer without taking its address and turning it into a double pointer. Type-mismatched forwarding (passing `&vec[string]` to `&vec`) remains rejected, and read-only and move rules remain unchanged.

## Type Parameter Constraints

Type parameters of generic functions can carry constraints: `fn add[T: Add](a: T, b: T) -> T { return a + b; }`. Multiple constraints are joined with `+` (`T: Add + Eq`), and different parameters are specified individually (`fn f[T: Copy, U: Ord](...)`). Constraints are only permitted on generic functions; writing constraints on generic structs and generic enums will be rejected.

Four built-in constraints are provided, with fixed, non-customizable names:

| Constraint | Allowed Arguments | Corresponding Language Capabilities |
| --- | --- | --- |
| `Add` | `i64`, `string`, `f64` | `+` (addition or string concatenation) |
| `Eq` | `i64`, `bool`, `string`, `f64` | `==`, `!=` |
| `Ord` | `i64`, `f64` | `<`, `<=`, `>`, `>=` |
| `Copy` | `i64`, `bool`, `f64` | Values can be repeatedly read without requiring drops |

Constraints are checked at two levels, **both of which only reject and never permit**:

1. **Call Site** (ADR-33): Checks whether the argument type is in the allowlist of each constraint; the error message lists the types permitted by that constraint. Constraints on `pub fn` across files are also enforced at the caller's call site.
2. **Declaration Site** (ADR-40): For **constrained** generic functions, the **intersection** of all constraint allowlists is taken as the set of valid types. The compiler then scans the function body for operations applied to type parameters; if a type in the valid set does not support such an operation, an error is reported at the type parameter declaration. For example, `fn f[T: Copy](a: T, b: T) -> T { return a + b; }` will report `the constraint still admits bool, which does not support it`, because `Copy` allows `bool` while `bool` does not support addition. Changing this to `T: Add` (or `T: Add + Copy`) resolves the issue. Conversely, `fn f[T: Ord](a: T, b: T) -> T { return a + b; }` is valid: `Ord` only allows `i64`/`f64`, both of which support `+`.

The declaration-site check is a **tightening** measure: previously, such declarations would pass and only report errors during instantiation with unsuitable types. Now, if the declaration itself is self-contradictory, it will fail to compile, even if there is no intention to call it with invalid types. The migration path is to tighten the constraints or remove them to revert to per-instantiation checking. This is a conservative diagnostic, not a formal proof: requirements are only recorded when an operation token is immediately adjacent to an identifier bound to a type parameter; call results, subscripts, fields, and indeterminate local variables are skipped. Unconstrained generics are not subject to this check. Therefore, **false negatives are permitted** (errors will still be caught during instantiation), but **false positives are not**.

The function body still undergoes a full type check for every instantiation; constraints do not participate in code generation, do not affect release paths, and are not a dispatch mechanism. `fn f[T: Printable]` (unknown constraint) and `T: Add + Add` (duplicate constraint) report errors at the declaration site; `add[bool](...)` reports `type argument 'bool' for 'add' does not satisfy 'Add'; that constraint allows i64, string, f64` at the call site. See `examples/constraints.ae` and `examples/generic_constraints.ae` for examples.

Traits (user-defined constraints, `impl`, static dispatch, method tables, and orphan rules) have not yet been implemented; there is currently no syntax for users to extend constraint types, and ADR-40 does not claim that traits are implemented.

## Current Implementation Limitations
The compiler currently limits expression nesting depth and the number of expression nodes to 128 each, block nesting depth to 64, and loop nesting to 64; errors are reported when these are exceeded. These are resource constraints of the early implementation, not final language capability commitments. Move/ownership tracking covers all owned types: `string`, `vec`, `map`, and struct variables share the same `moved` set (recorded by the compiler as `MoveKind::{Var, Field, StrVecElement}`). Struct fields and `vec` elements cannot be moved out by design and can only be used as borrows (see above for specific compile-time/runtime boundaries). Comparisons are not linkable; strings are immutable (no in-place modification); these limitations will be gradually lifted in subsequent versions according to the specification. Generic borrowing `&T` currently only covers `string`/`vec`/`vec[string]`, and when instantiating another `&T` template within a generic body, the call syntax changes according to the type argument (see above); this is also an implementation boundary rather than a final design commitment. Floating-point numbers only support `f64`: there is no `f32`, no decimal type, no math library, and `f64` cannot be stored in containers; explicit conversion is required between `i64` and `f64`, and conversions only accept values that do not lose precision. Package-level incrementality is currently limited to "runtime on-demand pruning" and "interface summary diagnostics": user modules are still treated as a single translation unit, modifying a function body will recompile parts of the program, and interface summaries do not yet participate in cache invalidation; parallel scheduling, module-level object files, and true "no-rebuild for unrelated packages" are not yet implemented. The declaration-site capability coverage check (ADR-40) only examines identifiers immediately adjacent to operation tokens and does not perform data-flow proofs on non-substituted generic ASTs: `&T`, composite types, subscripts/fields/call results, and indeterminate local variables are skipped and left to the per-instantiation check; therefore, it **may produce false negatives, but will not reject declarations that are otherwise valid**. `GenericFn` previously saved the entire token stream and source copy for each generic declaration per ADR-31, leading to O(N²) complexity in the frontend when the number of declarations was large; ADR-41 changed this to use `Rc` to share tokens by source file, eliminating this bottleneck as neither declarations nor instantiations copy the full token stream. `bench/shared_tokens_timings.py` can be used to compare binaries before and after the change in the same run, asserting that the generated C and declaration-site diagnostics remain consistent.
