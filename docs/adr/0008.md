# ADR-8: Strings are now NUL-terminated C-strings; length-prefixed representation is the established evolution path

- **Background**: The simplest string representation for the C backend is `char *`. Empirical testing (Workload B, 20k lines/1.4 MB) showed that `slice` requires `strlen` for positioning on every call, causing grep performance to degrade from 5.81 ms to 202 ms (40×) when slicing by line, exposing the cost of this representation.
- **Decision**: The current version retains the `char *` representation; `len`/`slice`/`bytes` are O(n). File search benchmarks remain naive byte scans (O(1) indexing for `vec`) rather than line-based slicing. `contains` utilizes the platform's `strstr`. Evolution path (to be addressed in a separate item): transition strings to a length-prefixed internal representation or borrowed views (Scheme §4.2) to make `len`/`slice` O(1), then re-test Workload B.
- **Evolution (2026-11-10, implemented)**: Strings changed to length-prefixed `ae_string {ptr, len}`—`len`/`slice` are now O(1), concatenation no longer requires scanning, `write_file` is binary-safe, and `bytes()` iterates based on length. All 70 tests maintain identical semantics.
- **Remaining Gap (Workload B empirical results)**: Sliced grep 7.58 ms > Naive 5.81 ms > reference 4.41 ms—each line `slice` still triggers an allocation (20,000 mallocs). Next step: borrowed views (`&str`-style zero-copy slicing, Scheme §4.2 "Distinguishing owned strings from borrowed views") to eliminate slicing allocations; this is a separate design window.
- **Consequences**: `len`/`slice` time complexity meets targets; allocation costs for line-based slicing remain high, so benchmarks continue to use naive byte scanning with transparent disclosure. NUL-termination semantics only affect `contains` (`strstr` semantics); `len`/`bytes` are now precise based on length.
- **View Evolution (2026-11-10, implemented)**: `ae_strview {ptr, len}` borrowed views + `slice_view` zero-copy slicing + borrow tracker (base variables cannot be moved/reassigned during view lifetime; containers cannot be modified during borrow period) + `for x in vec[string]` view iteration. View-based grep 7.34 ms—slice allocation is eliminated; the remaining bottleneck has shifted to the byte-by-byte bounds-checked loop (1.4 million checked accesses), which is a matter of standard library maturity (e.g., `memchr`-style line scanning) rather than representation.
- **Fusion Path (2026-11-10, implemented)**: `count_lines_with(text, pattern)` is now a single-pass, zero-allocation operation (`memchr` to find lines + first-byte `memchr` to skip intra-line searches). Workload B fused version 2.14 ms, faster than the compositional 4.72 ms baseline (2.2×) and all other references; compositional `lines()` + view + `contains` remains at 6.37 ms for comparison. The standard library provides fused primitives for hot paths and compositional primitives for readability.
