# Negative Claim Checklist

> Migrated from Proposal v0.2 §20.4 (2026-11-12). No external statements (READMEs, release notes, reports) may exceed the following items; entries are revised by corresponding ADRs as capabilities change. General rule: Claims must simultaneously satisfy **Dual-Platform Verification + Re-runnable Reports + Fair Comparison** (Proposal v0.3 §7.3).

1. Do not claim "memory-safe language achieved": Currently, it is restricted borrowing + compile-time move sets + runtime sentinels.
2. Do not claim Go-level compilation speed or Rust-level performance/safety guarantees, nor claim that low CPU, memory, or disk footprint targets have been met.
3. Do not claim to surpass Go or Python: There is no shippable comparison report with fixed versions, equivalent features, and identical inputs.
4. Do not claim that the generated C is free of undefined behavior under all inputs: Sanitizers and allocation counters only cover listed test cases.
5. Do not claim that the existing content-addressed cache is equivalent to package-level incremental builds, nor claim that cache-hit results can replace cold-build measurements.
6. Do not claim compatibility with the Python ecosystem, support for GPU/networking/threads, or that "all tasks can be completed in a single language."
7. Do not write new features that passed on a single platform as dual-platform verified; status is upgraded only after running the full command suite on both platforms.
8. Do not claim that `f64` is bit-wise identical to the C math library (the math library is not yet provided), nor describe the canonical text form as "shortest decimal": It takes the shortest significant digits that can round-trip, taking the shorter one between fixed-point and scientific notation.
9. Do not claim that W3 package-level incrementality is complete, nor claim "modifying one function body does not rebuild unrelated packages": Currently, only on-demand runtime pruning and interface summary diagnosis are achieved, user modules remain in the same translation unit, and summaries do not participate in cache invalidation decisions.
10. Do not write schemes refuted by actual measurements as achievements: PCH (69 MB cache traded for ~0.8s) and separate translation units (cold build regression ~68%, hot only faster by ~18%) have been rolled back; nor should Linux compilation time be treated as Windows compilation speed, as the two are separated by an order of magnitude due to `<windows.h>`.
11. Do not claim "removed dependency on `<windows.h>`" or "W6 handwritten minimal Win32 declarations implemented": ADR-39 only allows programs that do not touch the Win32 layer to stop including this header; programs using files, directories, clocks, environment, working directories, or subprocesses will still parse it, and no ABI assumptions are introduced. Do not present header file benefits on the Windows side as cross-platform benefits (Linux does not preprocess this branch anyway), nor treat cross-session absolute wall-clock values as precise speedups.
12. Trait/impl static dispatch has been implemented (ADR-47, dual-platform), but **do not claim a complete trait system**: no `&T` trait parameters, no generic impls, no default methods, no dynamic dispatch, no associated types/where clauses; trait methods cannot be called directly outside of generic bodies (inherent methods are a different mechanism — item 26). Also, do not describe the pre-check at the declaration site in ADR-40 as "constraints proving generic bodies valid" (false negatives are allowed, false positives are not). Do not claim "zero compilation time regression", do not treat upper-bound differences in `constraint_audit_timings.py` as pure audit cost (they include existing O(N²) token copying), and do not subtract absolute cross-session wall-clock values.
13. Do not describe "files with many generic declarations getting faster" as "compilers generally being N times faster": ADR-41 eliminates frontend copying which is O(N²) relative to the number of declarations; differences in single-function programs are within measurement noise. Do not use the ratio of old/new binary comparisons as a general speedup, do not subtract absolute values across archives, do not claim specific figures for peak memory reduction (uncampled), and do not ignore or treat differences in comparison environments (such as CRLF introduced by `git archive`) that cause "generated C to be byte-for-byte identical" as semantic changes.
14. Do not describe `check --json` as a language server or complete editor protocol (ADR-48): No incrementality, no error recovery (arrays currently have at most 1 element), start positions only; `message` is presentation text and is not guaranteed to be verbatim stable, editors should rely on `file`/`line`/`column` as the contract. Nor claim "checking does not require building" as a universal truth—it only holds for `check`/`check --json` (pure frontend), while `run`/`build` still require a C toolchain.
15. Do not describe the arena optimization of `split`/`lines` as zero-copy or universal speedup (ADR-49): Elements still copy bytes and carry their own NUL, covering only these two built-ins; vectors for `push`/`args`/`keys` remain element-wise owned. Do not treat the 1.84x/2.45x text payload speedup as a general speedup, nor claim peak memory reduction (uncampled). Executables of programs using fused paths will grow larger (`split_arena.ae` +2,341 bytes), and this cost must not be omitted.
22. Do not describe ADR-57 as "maps got faster": The time ratios of 1.012x / 1.027x are on the edge of noise; phrase it as "same speed, less memory"; the benefits are table body −22%, peak −15% (3.43 → 2.90 MB, now lower than Rust's 3.04); this is internal layout, `keys()` order and hashing remain unchanged; memory figures are VmHWM peaks including key strings, not the table body alone.
21. Do not treat the 1.17x speedup in ADR-56 as a general speedup: The benefits are payload-dependent (probe-dense tables show significant gains, small tables with a few keys show almost no difference), while the memory cost applies to all tables (32 bytes per slot + 0.5 load factor, 10,000-key table 512 KB → 1 MB, payload peak 2.44 → 3.43 MB); `keys` are sorted by byte order, iteration order and observable behavior remain unchanged; hash function is unchanged, nor should it be claimed that "maps are faster than Rust" (still 4% slower, 10% more memory); the reason string allocated on `map_get` miss (~6.9 ms for 1M iterations) was merely measured, not fixed.
20. Do not describe ADR-55 as "all characters can be displayed": Whether a console can display a certain character is determined by itself; conhost replaces non-BMP characters like emojis with `U+FFFD`, independent of code pages (936 is the same as 65001; probes calling `WriteConsoleW` directly behave similarly, independent of the runtime), whereas the same text written to a file remains complete UTF-8; only stdout is handled (runtime error messages are ASCII and remain `fprintf`); neither the console code page nor other global console states are modified; console output is unbuffered, with one system call per line; the cost is generated C `print(1)` +3,902 bytes (+34%), programs that do not print +525 bytes, build time within noise +1 ms, no regression in console throughput.
19. Do not describe ADR-54 as "encoding issues are fully resolved": Command-line arguments are converted to the ANSI code page by the CRT before entering `main`; characters that cannot be represented by the code page (some emojis) are lost and unrecoverable; only `args()` is fixed, console output encoding and `AE_CC`'s own path are separate topics; the cost is that programs calling `args()` retain `<windows.h>` on Windows (programs not using `args()` still drop the header).
18. Do not describe `tokenize` as a general iterator or "`split` got faster" (ADR-53): It only has a single form of "string + delimiter", has no `len` (counting requires consuming the entire stream), cursors cannot be printed/entered into containers/returned, and the delimiter upper bound is 16 bytes; `split` is unchanged by a single line, what gets faster is the exact same program written using a different pattern; the 2.59x speedup comes from "no longer materializing 450,000 tokens", and for inputs with very few tokens, the two writing patterns are nearly identical; do not confuse Windows' 1.22x with Linux's 2.59x, and absolutely do not compare wall-clock figures across sessions (from this round onward, timing and peak memory are split into two passes, and early Windows figures run high).
17. (Refreshed 2026-11-15 for ADR-0205 L2.) A view of `p.name` no longer freezes the whole struct: a field write only conflicts with a view of **that very field**, and writes to sibling fields are allowed. Still prohibited and still claimable-as-missing: returning or storing views (no escape), nested-field views (`a.b.c`), fields of array/vector elements (`v[0].name`), non-string field views, and any claim of "a general borrow checker" — L3/L4/L5 (escape, element borrows, Mut-loan generality) are unimplemented.
23. Do not describe ADR-59 as "faster compilation": What changes is the **optimization default for delivery artifacts**, making the build side more expensive instead (Linux +12.8–87.4 ms fresh-cache); runtime speedup figures are payload-dependent (Linux 1.34x–4.05x, Windows reports direction only due to process startup); flags sandwiched between arguments are still rejected; smaller `-O2` artifacts are observed natively under MinGW.
25. Do not describe ADR-61 as "generic containers": `vec[f64]` is a hand-written third family (`vec`, `vec[string]`, `vec[f64]`), `map` still only holds `i64`; explicit rejection of `sort`/`reverse` for vec[f64] is a design decision (NaNs lack a total order), not a defect; changing "indexing writes during cyclical borrowing" from allowed to rejected is a tightening of the rules (implementation catching up with existing documentation claims), not an exaggerated promotion of fixing a security vulnerability; changing `vec[1.0]` from rejected to legal is language evolution, and old test semantics have been updated accordingly.
24. Do not describe ADR-60 as "math library complete": Only 11 built-ins are provided (no `f32`, decimals, `min`/`max`, `vec[f64]`); `sqrt(-1)` → `nan` is an **intentional asymmetry** with `/`'s checked division-by-zero, not an omission; transcendental function texts only guarantee that "exact values and `nan` spellings match on both platforms", and byte-for-byte identical printed text holds only for exact values; the precision of `pow(2,10)=1024` is a practical property of libm (measured natively on glibc/UCRT), not a guarantee of the standard.
16. Do not describe the benefits of ADR-50 as "compiler generally speeding up by 10%+": It is a **constant** benefit of compiling ~14 KB less text per program, with the proportion shrinking as programs grow larger; the 11.4% end-to-end cold build speedup is larger than the single-file gcc difference, the mechanism is not fully attributed, and only measured values are reported; nor claim that executables become smaller (they remain unchanged) or that peak memory drops.

26. (Refreshed 2026-11-15 for ADR-0184–0187.) Inherent `impl Type` now supports by-value, `&self` (auto-borrow over struct borrows), and `&mut self` receivers on structs **and enums**, associated functions, `Self`, and generic impl blocks — do not describe methods as by-value-only anymore. Still true, still claimable-as-missing: no trait objects/dynamic dispatch, no default method bodies, no associated types or where clauses, no orphan-rule generality beyond same-file, methods resolve statically with no method table, and trait methods still dispatch only through generic bounds (a different mechanism from inherent methods).
23. 不得宣称 M2.13 的 24 小时差分验收「已通过」或「已基本完成」：截至 2026-11-15 仅累计约 5 小时段（Windows 段 1/2/3、Linux fuzz4 干净前缀与 fuzz6，全部 0 failures），且中途有两起环境故障（磁盘满/tmpfs 满）被修复并核销；验收口径是累计墙钟达 24h、无未核销失败、四路一致。也不得把「0 failures」的段数说成小时数，或把单平台段说成双平台覆盖。
